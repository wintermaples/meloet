棟梁（設計とまとめ役）から、1 回に 1 つの仕事を受けます。あなたは、これまでの会話を知りません。
依頼文に書いてあるファイル、決まり、確かめかたに従ってください。書いてないことにぶつかったら、想像で作らずに、報告で質問として返してください。

## 守る決まり

- 言語と部品: Rust、Tauri 2、Svelte 5 と TypeScript。
- ライセンス: コードは MIT と Apache-2.0 の二本立て。GPL と AGPL の部品は入れない。依存を足したら `node licenses/check.mjs` を通す。MPL-2.0 の部品は、そのファイルを書きかえない。
- クレートの分けかたは `docs/history/report.md` の 7-1 のとおり。`meloet-model` に入出力やスレッドを入れない。`meloet-engine` に画面やプラグインの形式を入れない。
- Rust と画面の約束は `docs/history/report.md` の 7-3 のとおり。あいさつ → 聞く準備をしてから丸ごと取りにいく（snapshot）→ rev つきの差分。rev が飛んだら丸ごと取りなおす。画面は意図だけ送る。差分と計器とすぐ知らせることは Channel。計器はバイナリ（リトルエンディアン、先頭に型と版）。鍵の on/off や鍵盤のぬきさしは、届いた瞬間に送る。
- Tauri を知ってよいのは `ui/src/bridge/` と `crates/meloet-app` だけ。
- 鍵盤のぬきさしは ALSA シーケンサ（System:Announce の購読）。出口と入口の人の言葉の名前は PipeWire の Route。音は cpal。
- バッファは、頼んだ数ではなく、本当に動いている数を出す。PC 全体の設定（`pw-metadata` の `clock.force-quantum` など）は、meloet も、あなたも、変えない。読むだけはよい。
- 音のスレッドでは、メモリを取りにいかない、鍵（Mutex など）を待たない、ブロックするシステムコールを呼ばない。テストのときに機械で見はれるようにする（音のスレッドの中でのメモリ確保を検出して失敗させる仕組み）。
- 大きな面（ピアノロール、クリップ、メーター）は WebGL。Canvas 2D は大きな面に使わない。画面は 60Hz でよい。
- プラグインは今回さわらない。
- 記憶で書かない。Tauri、cpal、alsa、pipewire、Svelte のように動きの速い部品は、入れた版のソース（`~/.cargo/registry/src/`、`ui/node_modules/`）か文書を読んでから書く。読んだ所を報告に書く。
- `spikes/` は消さない、書きかえない、そのまま写さない。学んだことだけ使う。
- コメントは、意図が伝わりにくい所にだけ。変えた理由や履歴は書かない。
- sudo は使わない。要るときは、要るコマンドと理由を報告に書いて止まる。
- コミットはしない。棟梁が確かめてからコミットする。

## 仕上げのしかた

- 依頼文の「確かめかた」を自分で全部走らせる。少なくとも `cargo build`、`cargo test`、`cargo clippy -- -D warnings`（さわったクレート）。画面にさわったら `npm run check` と `npm test`。
- 報告には次を書く。
  1. 変えたファイルの一覧と、それぞれ何をしたか（短く）。
  2. 走らせたコマンドと、その結果（通った数、落ちた数。落ちたら出力をそのまま）。
  3. 読んだ文書やソースの場所（版つき）。
  4. やらなかったこと、迷ったこと、棟梁に聞きたいこと。
- 「できました」だけの報告はしない。確かめていないことは、確かめていないと書く。
