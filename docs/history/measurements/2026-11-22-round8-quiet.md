### すすめ: CPU の道（`WEBKIT_DISABLE_COMPOSITING_MODE=1` を meloet が決める）

- 理由 1（いちばん大きい）: 鍵 → 画面。合成の道は、どの場面でも p50 が 8〜10 ms 長く、ミキサーをひらくと「2 コマ以内」の見積もりが 92.5〜95 % に落ちる。WebKit のコマの決めかたから来るので、meloet の画面を軽くしても戻らない（読み。確かさ C）。CPU の道は 99.2〜100 %。
- 理由 2: ミキサーをひらいた再生（いちばん重い、よく使う形）は CPU の道のほうが軽い（busyMs 9.7 と 12.4 ms、WebKit の CPU 71 と 115 %）。合成の道では、上の帯とミキサーが同じコマで変わると、囲む四角が窓の高さになる（`2026-11-22-round8-webkit-2.52.6-2.md` 1 章）。
- 理由 3: メモリは CPU の道が少し少ない（WebKit 20〜65 MB、meloet 6 MB）。meloet の画面のプロセスの CPU も半分（何もない画面で 17.7 と 8.7 %）。
- 引きかえに失う物: **アレンジの横の送りと拡大は、CPU の道で 1 コマ 20〜24 ms（60 Hz を保てない）**。合成の道は 5〜8 ms。何もない画面 ・ ピアノロールの再生も、合成の道のほうが busyMs は小さい（どちらの道でも 60 Hz は保っている）。
- 送りの重さは、7 章の「CPU で描く WebKit」の決まり（よごれた四角の数と広さ）を送りに当てて削る宿題になる（`webkit-damage.sh` は CPU の道で使える）。

#### 案（書きかえはしていない）: 起動のいちばん初めに変数を決める

`crates/meloet-app/src/main.rs` の `JSC_OPTIONS` と同じ所、同じ「外で決めた値が勝つ」形で 1 行足す:

```rust
const JSC_OPTIONS: &[(&str, &str)] = &[
    ("JSC_useGenerationalGC", "0"),
    ("WEBKIT_DISABLE_COMPOSITING_MODE", "1"),
];
```

- 名前とコメントは「WebKitWebProcess が受けつぐ環境」にまとめなおす（`set_jsc_options` → たとえば `set_web_process_env`）。理由（鍵 → 画面、この測り）をコメントに 1 行。
- くらべる時は外から `WEBKIT_DISABLE_COMPOSITING_MODE=` を決める形になるが、**WebKitGTK 2.52.6 が空の値や `0` を「決めていない」と読むかは確かめていない**。くらべる道が要るなら、meloet だけの変数（たとえば `MELOET_WEB_COMPOSITING=1` で足さない）にするのが確か。
- ほかの形: `webkit2gtk` 2.0.2 の `Settings::set_hardware_acceleration_policy(HardwareAccelerationPolicy::Never)`（`src/auto/settings.rs`、`enums.rs`）を Tauri の `with_webview` から呼ぶ。wry 0.57.2 はこれを決めていない（`src` に名前がない）。2.52.6 で `Never` が `WEBKIT_DISABLE_COMPOSITING_MODE=1` と同じ道になるかは確かめていない。環境変数の形なら、この測りと同じ物。
- この PC 以外（Intel ・ AMD、ほかの版の WebKitGTK）でも CPU の道がよいかは測っていない。`.1` までのこの PC は、変数なしで CPU の道だった。

## 2. 16 トラックの Surge XT ＋ ZamComp（`app-watch.sh --seconds 170`、2.5 秒目にミキサー、7 秒目から再生、合成の道。横で `long_record_watch.py`、`plug_watch.py`、スレッドの優先度を読む `k8m-export-watch.py`）

- **xrun の秒に、エンジンの負荷は高くなかった**: 3 回めの xrun の前後（ページの 70〜80 秒）の 1 秒ごとの最大は 28〜42 %（ブロックの長さの半分より下）。BUSY もその秒 675 µs。第 7 回の 1 回めも、最大 109 % は xrun の 3 秒前だった。「ブロックの中の仕事がブロックより長くなった」形ではなく、**コールバックがおくれて呼ばれた**形に合う（推論。確かさ C）。
- **meloet の音のスレッドはリアルタイムでない**（この測りで見つけた事）: コールバックが回るスレッド `pw_out` は、どの回も `SCHED_OTHER`、nice 0（`/proc/<pid>/task/*/stat` の policy 0 ・ rt_priority 0。`ps -L -o cls` でも TS）。弾くほうのプラグイン係の音のスレッド `plughost-audio-*` は `SCHED_FIFO` 20。わけ: cpal 0.18.2 の PipeWire の出口は、コールバックを自分の main loop のスレッド `pw_out` で回し（`src/host/pipewire/stream.rs` 788〜792 行: `RT_PROCESS` をわざと立てない）、優先度を上げるのは `realtime` の機能のとき（`stream.rs` 237〜257 行、`audio_thread_priority`）だけ。meloet は `Cargo.toml` で `features = ["pipewire"]` だけで、自分でも上げていない（`crates/` に `sched_setscheduler` はプラグイン係の中だけ）。`docs/architecture.md` の 20 章や 22 章の「meloet の音のスレッドはリアルタイム」は、今のコードと合わない。
  - 見立て: 16 コアの静かな PC でも、ふつうのスレッドどうしの順番待ち（WebKit の主スレッド 80 %、プラグイン係の主スレッド、GTK）で、5.33 ms のブロックがたまにおくれる。xrun が 3 回に 1〜2 回、しかも負荷の山と同じ秒でない事と合う（推論。確かさ C）。
- 1 ブロックの中の時間（再生中 160 秒 ≒ 30000 ブロック）: 負荷の平均 10.1〜10.4 % ＝ 1 ブロック 0.54〜0.55 ms。そのうち返事を待った時間は Surge XT 3.5 秒 ＋ コンプ 6.2〜6.6 秒 ＝ 1 ブロック 0.33〜0.34 ms（約 6 割）。のこり約 0.2 ms がエンジンのほかの仕事。今の数では、待ちの中の「子が回っていた時間」と「起きるまで」は分けられない。
- **Surge XT の係が、再生を始めた所で止まった**: 19 回の Surge XT 16 の起動のうち 2 回（2 章の 1 回め、3 章の「なし」の 1 回め）。どちらも再生の頭（起動から 7.65 秒、`meloet: the process of vst3:ABCDEF019182FAEB566D624153675854 stopped (16 plugins)`）。返事なしの 5 秒（`HANG_MS`）より早いので、プロセスが終わった形（落ちた）。係の標準エラーは捨てているので、わけは見ていない。第 7 回の終わりの記録には出ていない。
