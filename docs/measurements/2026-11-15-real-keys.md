## 鍵 → 画面の形

Rust → 描いたの散らばり（2 ms ごとの鍵の数）:

| 状態 | 0〜2 ms | 2〜16 ms | 16 ms〜 |
|---|---|---|---|
| 止まっている | 150 | 152（2 ms ごとに 18〜27 で、ほぼ平ら） | 4 |
| 再生中 | 276 | 163（同じく平ら） | 10 |
| 録音中 | 127 | 107（同じく平ら） | 5 |

- 遅れはどれも、JS が受けてから描くまで（描いた − 受けた）の側にある。Rust → JS は小さい。
- 2〜16 ms の平らな散らばりは、画面がもう毎コマ描きつづけているとき（再生中の位置、弾いたあとのメーター）に、鍵が次の 60 Hz のコマを待つ形。ヤチヨさんの PC のコマの間は 16〜17 ms がほとんど（`frame-profile.json`、4000 コマ）。止まっているときに遅れた鍵は、前の鍵から 65 ms ほどしか空いていない鍵が多い（前の鍵のメーターが動いている最中）。
- 仮想の鍵盤の回は、ほとんどの鍵が 2 ms 以内だった（1920×1080 の再生中で 120 鍵のうち 105、毎コマ描きつづけているときでも）。

## 仮想の鍵盤で、コマの間を残して測りなおした（同じ日、`a8f8ae2` の release、エージェントのユーザー）

| 1920×1080 再生中 | Rust → JS p50 / p95 / 最大 | Rust → 描いた p50 / p95 / 最大 | 鍵 → DAC 平均 / p95 / 最大 |
|---|---|---|---|
| 257 ms ごと（いつもの） | 0.13 / 2.13 / 4.13 | 0.13 / 3.12 / 4.13 | 13.21 / 15.68 / 15.71 |
| 257 ms ＋ 0〜130 ms のばらつき（`--jitter-ms 130`） | -0.15 / 0.77 / 1.76 | 0.41 / 1.61 / 2.28 | 13.03 / 15.59 / 15.97 |

- コマの間は、どちらも 16〜17 ms がほとんど（60 Hz）。1 コマの仕事（`busyMs` p50 2 ms・p95 4 ms）も、ヤチヨさんの回と同じ。
- いつもの 257 ms ごとの回は、鍵が 120 回とも前のコマから 10〜16 ms の所（次のコマの直前）に来ていた。決まった間隔だと、コマの刻みとかみ合う。
- ばらつかせた回は、鍵が前のコマから 0〜16 ms に平らに散らばったのに、120 鍵とも 2 ms 以内に描かれた。この環境では、鍵が来るとすぐ次のコマが来る。
- つまり、ヤチヨさんの回とのちがいは、鍵の間隔でも 1 コマの重さでもない。のこる候補は (1) 動かした人の環境（ヤチヨさんのユーザーで、ヤチヨさんのターミナルから。エージェントは `dbus-run-session` つき）か、(2) 本物の鍵盤そのもの。ヤチヨさんのユーザーで `latency.sh`（仮想の鍵盤）を走らせると分けられる（確かさ C: 測った数からの読み）。
- ヤチヨさんのユーザーで同じ `latency.sh --state playing --jitter-ms 130` を走らせた: Rust → 描いた 0.58 / 3.37 / 5.80 ms、鍵 → DAC 13.06 / 15.48 / 15.92 ms。速いほう。だから「ヤチヨさんのユーザーかどうか」ではない。
- ヤチヨさんの本物の鍵盤の回では、待った鍵のコマは、前のコマからふつうの 16 ms のところに来ていた（鍵が来ても、コマが早まらなかった）。仮想の鍵盤の回は、どこで来ても早まった。
- のこる候補（確かさ C）: (1) 本物の鍵盤の出来事（和音、速い打鍵、アフタータッチや CC など、鍵のほかに来る物）、(2) `real-keys.sh` はふだんのセッションのバス（`dbus-run-session` なし。アクセシビリティのバスもふだんの物）、(3) ヤチヨさんの設定（窓の大きさ、拡大率、出口）。次の回で分ける。
- 「2 フレーム以内」は、どの回も 100 %。待った鍵は、画面に出るのが最大で 1 コマ（16.7 ms）おそくなっているかもしれない。
- 画面に光が出るのは、どちらにしても次の画面の刻み。ふだん使うときの見え方は、この本物の鍵盤の数のほうが近い。「2 フレーム以内」は、どの回も 100 %。
