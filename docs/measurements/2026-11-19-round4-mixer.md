# 第 4 回 区切り3 の測定: ミキサーが入った本物のアプリ（2026-11-19）

ミキサー（区切り3）が入った形で、8 トラックの曲を使い、鍵 → 画面 ・ 鍵 → 音、WebGL の文脈の数、10 分の録音、起動と読みこみとメモリ、処理の負荷を測った。くらべる相手は `2026-11-18-round3-followup.md`（以下「前」。1 トラック ・ 200 ノートの曲、ピアノロールをひらいた形）と `2026-11-18-round4-mixer-cpu.md`（オフライン、PC がこんでいた）。

## ひとめで

- **気になる数が 1 つ**: 8 トラックの曲を**再生しながらミキサーをひらいている**と、鍵 → 画面がおそくなった。間をあけた鍵で p50 8〜12 ms ・ p95 16〜18 ms（前は p95 1〜6 ms）。「2 コマ以内」が 87〜99 % で、線（33 ms）を 1〜3 ms こえる鍵がある。コマは落ちていない。鍵 → 音は変わらない。
  - 同じ 8 トラックの再生でも、ミキサーを閉じれば p95 2.2 ms。1 トラックならミキサーをひらいても p95 2.6 ms。**「たくさんのメーターが動く」と「ミキサーがひらいている」が重なったとき**だけ。
  - そのとき、ページの主スレッドは 1 コマ 16.7 ms のうち 13 ms ほどふさがっている（WebGL の係の仕事は 1 ms 以下。残りは、係のあとの時間 = 面を出す ・ スタイル ・ レイアウト ・ ペイント）。鍵の知らせは、そのあいだ待つ。
- WebGL の文脈: この PC でできるいちばん高い窓（ページ 2560×1403）で、アレンジ ・ ピアノロール ・ ミキサー ・ 音の設定をひらいて、作った数 8 ・ いまある数 8 ・ 失われた数 0。帯をひらいたり閉じたりしても 8 のまま。**予算 12 の中**。最大の 10 になる形（ページの高さ 1676 以上）は、この画面では作れなかった。
- 10 分の録音（8 トラックを鳴らしながら、ミキサーをひらいたまま）: 録音中の xrun 0、2106 音が全部入った。WebKitWebProcess 366 → 388 MB（最大 390。前 340 → 409）。本体は 904 MB で動かない。
- 起動: 起動 → 最初のコマ 0.67〜0.74 秒。包みがあってもなくても同じ。グランドピアノは起動から 0.35 秒で読みおわる。8 トラックの曲の 6 音色は 0.73 秒で読みおわる。
- メモリ（本体の RSS）: 包みなし 216〜224 MB、グランドピアノ 565 MB、8 トラックの曲 902 MB。
- 処理の負荷: 8 トラックの再生で平均 5.3 % ・ 最大 10.8 %（アプリの中の数）。オフラインの 16 トラックは静かな PC で平均 8.4 % ・ 最大 13.8 %、1 ms をこえたブロックは 0。

### 前とくらべる（Rust → 描いた p95、ms）

前は 1 トラック ・ ピアノロールをひらいた形、今回は 8 トラック ・ ミキサーをひらいた形なので、同じ形のくらべではない。

| | 前（1 トラック、ピアノロール） | 今回（8 トラック、ミキサー） |
|---|---|---|
| 止まっている spaced | 1.20 | **14.30** |
| 止まっている mixed（間をあけた / すぐあと） | 15.35 / 15.29 | 10.62 / 14.04 |
| 再生中 spaced | 5.61 | **15.72 ・ 17.94 ・ 15.08** |
| 再生中 mixed | 14.06 / 16.51 | 15.90 / 18.96 |
| 録音中 spaced | 1.11 ・ 4.68 ・ 0.88 | **8.56 ・ 11.46** |
| 録音中 mixed | 10.60 / 16.92 ・ 13.38 / 12.78 | 12.32 / 10.11 |
| 鍵 → DAC p95 | 15.60〜15.87 | 15.44〜15.84 |

- **鍵 → 音は変わっていない**（8 トラックとミキサーを通っても、平均 13.1〜13.5 ms）。
- **鍵 → 画面は、間をあけた鍵でおそくなった**。前は「すぐ描く」（p50 1 ms）だったのが、今回は「次のコマまで待つ」鍵が多い（再生中 spaced は 120 鍵のうち 119 鍵が 2 ms より長く待った）。Rust → JS（ページが知らせを受けとるまで）がすでに p50 7〜11 ms なので、描くのがおそいのではなく、ページの主スレッドがふさがっていて受けとれない。
- 再生中は「2 コマ以内」が 87〜99 %。こえた鍵は 16.7〜19.9 ms ＋ 1 コマなので、線を 0〜3 ms こえる。3 コマ（50 ms）はどの鍵も守った。
- 録音中が再生中より少しよいわけは、わからない（2 回ともそうだった。取りなおしの数が足りない）。

### どこが重いか（切り分け、再生中 spaced）

| 曲 | ミキサー | 鍵 → 画面 p50 / p95 / 最大 | 2 コマ以内 | 係のあとの時間 p50 / p95 / 最大 | コマの間 p95 / 最大 |
|---|---|---|---|---|---|
| 8 トラック | ひらく | 11.72 / 15.72 / 17.72 ・ 7.93 / 17.94 / 19.93 | 98 % ・ 87 % | 13 / 16 / 32 ・ 13 / 16 / 35 | 17 / 20 ・ 18 / 21 |
| 8 トラック | 閉じる | 1.24 / 2.23 / 3.23 | 100 % | 6 / 11 / 26 | 17 / 18 |
| 1 トラック | ひらく | 0.60 / 2.60 / 5.60 | 100 % | 4 / 11 / 20 | 17 / 17 |
| 1 トラック | 閉じる | 0.99 / 4.99 / 7.99 | 100 % | 2 / 5 / 13 | 17 / 18 |

「係のあとの時間」は `frame-profile.json` の `busyMs`（WebGL の係のコマの始まりから、そのとき投げた知らせが走るまで。ms、整数に丸めてある。後ろ半分のコマ）。係の中の仕事（`glMs` など）は、どの回も p50 0 ・ p95 1 ・ 最大 2 ms。

- 重いのは WebGL の係の中ではなく、**そのあと**（面を出す、スタイル、レイアウト、ペイント）。メーターの面が 1 コマに描かれる回数は、8 トラックでミキサーをひらくと、`trackMeters` ・ `mixerMeters` ・ `masterMeter` がほぼ毎コマ（2766 コマで 2508 ・ 2752 ・ 1704 回）。
- 読み（確かめていない）: 動くメーターの面が大きく ・ 多くなると、面を出す時間がふえる（7 章の「面を 1 回出すたびに主スレッドが止まる」）。8 トラックだと `trackMeters`（8 行ぶんの高さ）と `mixerMeters`（11 本のストリップをまたぐ幅 × メーターの高さ）の 2 枚が毎コマ出る。1 トラックならどちらも小さい。HTML のほうに毎コマ変わる物があるかどうかは、見ていない。
- 止まっているときも、鍵を弾くとそのトラック ・ 戻り A ・ マスターのメーターが動くので、同じ形になる（止まっている spaced の p95 14.30 ms、係のあとの時間 p50 3 ・ p95 15 ms）。
- 10 分の録音のあいだ、WebKitWebProcess は CPU 1 本の 83 % を使っていた（`ps` の `pcpu`、始めから 6 分目までの平均。1 回だけ読んだ）。

## 5. 処理の負荷

### アプリの中（8 トラックの曲を再生、ミキサーをひらいたまま）

`tools/measure/app-watch.sh --seconds 80 --song band8-32.meloet --commands '…toggleBand mixer…, …playStop…'`。ページの中の係が、計器で届く「処理の負荷」（最後のブロックにかかった時間 ÷ ブロックの長さ。1 秒に 60 回）を 1 秒ごとにまとめる。再生している 65 秒（3900 回）の数。

| 曲 | 平均 | 最大 | 1 秒ごとの平均 |
|---|---|---|---|
| 8 トラック（1 回目） | 5.26 % | 10.5 % | 4.8〜5.9 % |
| 8 トラック（2 回目） | 5.36 % | 10.8 % | 4.9〜6.1 % |
| 1 トラック（グランドピアノ） | 2.11 % | 4.5 % | 1.5〜2.5 % |

- 計器は「読んだときの最後のブロック」なので、60 回 / 秒の抜きとり（ブロックは 187 回 / 秒）。最大は、抜きとった中の最大。変わりが 1 % より小さいときは前の値のまま送る決まり（`LOAD_STEP`）なので、平均は 1 % ほどの幅でしか言えない。
- 外から見た数（10 分の録音の `pw-top` の BUSY、平均 4.9 % ・ 最大 9.4 %）と合う。

## わかった事 ・ わからなかった事

- わかった: 鍵 → 音、xrun、メモリの流れ、文脈の数、起動、エンジンの重さは、ミキサーと 8 トラックが入っても線の中。
- わかった: 鍵 → 画面は、「8 トラックが鳴っている ＋ ミキサーをひらいている」ときに、ページの主スレッドが 1 コマのうち 13 ms ふさがり、鍵が次のコマまで待つ。線（2 コマ）を数 % の鍵が 1〜3 ms こえる。
- わからなかった: その 13 ms の中身（面を出す時間か、HTML のスタイル ・ レイアウトか）。`JSC` や WebKit の計時は取っていない。
- わからなかった: 窓そのものが画面に出る時刻。ページの最初のコマで代えた。
- 測っていない: 文脈が 10 になる形（画面の高さが足りない）。ピアノロールとミキサーを両方ひらいた形での鍵 → 画面と 10 分の録音。16 トラックより多い曲。本物の鍵盤。

## 直した道具

- `tools/measure/make_song.py`: `--tracks N`（版 3、上の表の 8 音色を順に）。`--tracks` なしは前と同じ（版 1）。`test_make_song.py` に試験を足した。
- `tools/measure/latency.sh`: `--mixer`（ミキサーの帯をひらく）。`--song` は `--piano-roll` なしでも使える。
- `tools/measure/long-record.sh`: `--mixer`、`--song`。
- `tools/measure/long_record_watch.py` ・ `long_record_summary.py`: `pw-top` の BUSY（ストリームのコールバックにかかった時間）も 1 秒ごとに書く。`pw-top` の QUANT はストリームが頼んだ数で、動いている数ではないので、割合は出さない。
- `tools/measure/app-watch.sh` ・ `app_watch_summary.py`（新しい）: 本物のアプリを決めた秒数だけ動かし、起動からの時刻（ページ、最初のコマ、音色の読みおわり）、文脈の数、処理の負荷、RSS を書く。
- `ui/src/dev/watch.ts`（新しい）、`ui/src/dev/start.ts`: `MELOET_UI_SCRIPT=watch` のとき、ページの中で処理の負荷と文脈の数を書く（`app-watch.json`）。`MELOET_MEASURE_DIR` と `MELOET_UI_SCRIPT` があるときだけ `import()` される所なので、ふだんの道は同じ。
