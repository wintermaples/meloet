## 2. 書いた点の位置（`tools/measure/auto-write.py`、新しい道具）

本物のアプリ（`remote.py`）でミキサーをひらき、音量の「● 書く」をオンにして始め、トラック 1 のフェーダーに、ページの中で作ったポインタの出来事（押す → 約 230 ms おきに 6 回動かす → 離す）を 20 回送る。保存した曲の帯の点を読む。

- **頼まれた形から変えた所**: meloet の窓は Wayland の窓なので、X の作り物の出来事は届かない（`remote.py` の X の道具は、プラグインの窓のための物）。代わりに、ページの中で `PointerEvent` を作って送った（`remote_page.js` の `ptr`）。だから**マウスからページまでの道は、数に入っていない**。
- 動かした時刻は、出来事を送る直前の `Date.now()`（1 ms きざみなので、読みに 0.5 ms 足した）を、Python で CLOCK_MONOTONIC にした物（アプリを通らない）。`performance.now()` も、この WebKitGTK では 1 ms きざみだった。
- ものさしは 2 つ:

### 原因（gdb の呼び出しの列と、WebKit のソースで確かめた）

毎コマ、決まった大きな四角が `setNeedsDisplayInRect` に来ていた（8 本: `0,45 1113×779` ・ `0,824 1199×55` ・ `0,879 1200×29` ・ `0,908 1199×8` ・ `0,916 1204×116`。16 本: `0,0 1920×1080`）。頼んでいるのは、canvas でも数字の箱でもなく、**レイアウトの終わり**:

```
WebCore::Document::updateLayout
 → WebCore::RenderView::RepaintRegionAccumulator::~RepaintRegionAccumulator
 → WebCore::RenderView::flushAccumulatedRepaintRegion
 → WebCore::ScrollView::repaintContentRectangle
 → WebKit::WebChromeClient::invalidateContentsAndRootView
 → WebKit::DrawingAreaCoordinatedGraphics::setNeedsDisplayInRect
```

- **WebKit の、もう 1 つの決まり**（`Source/WebCore/rendering/RenderView.cpp` の `accumulateRepaintRect`、枝 `webkitglib/2.52`。確かさ A、meloet-research が読んだ）: 1 回のレイアウト（とスタイルの計算）の間に出た描きなおしの四角は、1 つの Region にためる。その Region の **`gridSize()`（y の帯の数 × x の区切りの数。`Region.h`）が 256 をこえると、そこまでの四角を「ぜんぶを囲む四角」1 つにする**。その四角が窓の 75 % 以上なら、窓ぜんぶにする。
  - これは、7 章の「11 個以上か 25 %」（`DrawingAreaCoordinatedGraphics` の決まり）より**前**に効く。上下左右のそろっていない小さな四角は、6〜8 個で 256 をこえる。
  - `cover`（canvas の下に入れる）は、あとの決まりにしか効かない。ここで囲む四角になった物は、canvas の外まで広がる。
- **1 回のレイアウトで出る四角**（`rects-band8-vol/rects.txt`、`RenderView::repaintViewRectangle` で読んだ）: ストリップ 1 本につき、目盛の字 6 つ（`17.6,704 14×16` …）、メーターの所、値の行、「オートメーション」の行、M S ● の行、ストリップの下の箱 …。しかも**同じ箱が 116 px ちがう 2 つの高さ**で出ている（値の行が y 832 と 948、次の行が 851 と 967）。フェーダーのつまみ（`top: N%`）か値の文字が変わると、**そのストリップの縦の flex がまるごとレイアウトしなおされ**、途中の形（のびる前）と終わりの形の両方が描きなおしになる。8 本ぶんで数百個になり、Region はすぐ囲む四角になる。
- ページの中で、1 つずつ消して測った（8 本、音量の帯、ミキサー。busyMs の平均。`js-band8-vol*`）:

| 形 | busyMs |
|---|---|
| そのまま | 21〜23 ms |
| つまみを消す（`display: none`） | 21.4 ms |
| 値の文字を消す | 18.0 ms |
| つまみと値の文字を消す | 8.7 ms |
| つまみ ・ 値の文字 ・ アレンジの帯の見出しの値を消す | 6.8 ms（帯なしの 6.0 ms にほぼ戻る） |

| `visibility: hidden` で 3 つとも見えなくする | 21.0 ms（変わらない。描く中身ではなく、レイアウトが原因） |

### 直しかたの案（直していない。棟梁と決める）

ページの中で、にせの部品を足してためした（`js-band8-vol-fix`）:

| ためした形 | busyMs |
|---|---|
| つまみを `transform: translateY()` で動かす（値の文字と帯の値は消す） | **8.9 ms**（62 コマ/秒に戻る） |
| 値の文字を、`position: absolute` の箱（`contain: strict` あり ・ なし）に入れる（つまみと帯の値は消す） | 16.1 ・ 16.8 ms（まだ重い） |
| 上の 2 つを合わせる | 15.8 ms |

- **案 A（つまみ。効くと確かめた）**: フェーダーのつまみ、パンのつまみ、センドの棒を、`top` や `width` ではなく **`transform` で動かす**。再生の位置の線と同じ考え（7 章）。レイアウトが走らないので、ためる Region に入らない。
- **案 B（値の文字。まだ答えがない）**: 文字が変わると、行のレイアウトは必ず走る。箱を閉じても（`contain: strict`、`position: absolute`）軽くならなかった。理由は調べきれていない。考えられる道:
  - B-1: オートメーションで動いている間、値の文字を 1 秒に 10 回までに間引く（区切り1 のたたんだテンポの行と同じ。数字は、どのみち 60 Hz では読めない）。それでも、変わるコマは囲む四角になるので、**ストリップ 8 本の文字を同じコマでまとめて変える**（10 回/秒 × 1 コマ）形にする。
  - B-2: 動いている間の値の数字を、WebGL で描く（メーターと同じ canvas。字の形を持つ必要がある。大きい）。
  - B-3: 値の文字の箱を、ストリップの flex の外（ミキサーの箱の上に重ねた 1 枚の層）に出し、ストリップのレイアウトをよごさない。ためしていない。
- **案 C（アレンジの帯の見出しの「いま −7.4 dB」）**: B と同じ。B-1 の間引きが、いちばん小さい。
- **どれを先にしても**: 足したら `webkit-damage.sh` だけでなく、**レイアウトでためる Region の決まり**も見る。道具は下の `k6meas2-rects.py` の形（`RenderView::repaintViewRectangle` と `flushAccumulatedRepaintRegion` を読む）を `tools/measure/` に入れるのがよい（今回は入れていない）。7 章の「あとから 60 Hz で動く物を足す人が守る事」に、「毎コマ変わる物は、レイアウトを走らせない（transform だけ）。文字を毎コマ変えない」を足すのがよい。

## 4. 10 分ずっと書く（`auto-write.py --long 600 --hold-ms 2000`）

再生しながら、音量のフェーダーを毎コマ動かし（ゆっくりの波 ＋ 速い波 ＋ 小さなぎざぎざ）、2 秒ごとに離して押しなおす（離すたびに 1 手）。この回の間、横で 3 の gdb の測りを 2 つ走らせた（RSS は見られるが、にごっている）。

| | 数 |
|---|---|
| 手 | 282 |
| 送った動き | 46817 |
| 帯の点（間引きのあと） | 1 → 25002（1 手に約 89 点。送った動きの 53 % が残った） |
| 履歴が持つ点の写し（手ごとの、その時の帯の点の数の和 × 16 バイト） | 353 万点 = **53.9 MiB** |

- 「人が 10 分、2 秒ごとに離しながら書きつづける」は、きつい形。離す間が長ければ手が少なく、写しも少ない（10 秒ごとなら、同じ点の数で約 1/5）。

## 6. 「出口を録ると、5 秒おきくらいに 768 か 1024 こま抜ける」を、もう一度

出口のモニターを `pw-record` で録りながら、横で `pw-top -b`（どのノードの ERR も、1 秒に 1 回）と `pw-mon`（グラフの出来事）を、時刻つきで書きとめた。曲はノートなし、テンポ 120（クリックは 24000 こまおき）。60 秒ずつ。

|---|---|---|---|---|
| app1 | 本物のアプリ（WebView あり）、メトロノーム | 1 本 | 18.0 秒 −768、28.0 秒 −768、46.0 秒 −768 | **`pw-record` だけ**（18.2 秒に 0 → 7、28.2 秒に 14、46.2 秒に 21） |
| app1b | 同じ | 1 本 | 13.0 秒 −768、18.0 秒 −768、42.4 秒 −768、52.4 秒 −1024 | `pw-record` だけ（13.1 秒 7、18.1 秒 14、43.1 秒 21、53.1 秒 30） |
| app2 | 同じ | 2 本 | 1 本め: 6.5 秒 −1024、13.0 秒 −768、43.0 秒 −768、47.9 秒 −768。2 本め: 13.0 秒 −768、33.0 秒 −1280、42.9 秒 −768、47.9 秒 −768 | `pw-record` だけ（2 本の和で 32） |

どの回でも: meloet のストリームの ERR は 0 のまま、`pw-play` も 0 のまま、アナログの出口の ERR は 1 のまま（ひらいた時の 1）。抜けの前後 1 秒に、`pw-mon` の出来事（ノードやつなぎが足された ・ 消えた ・ 変わった）は 1 つもない。

**わかった事**:
- **meloet がなくても起きる**（`pw-play` ＋ `pw-record` だけで、同じ形の抜け）。meloet の音の道の不具合ではない。WebView のあるなしも関係ない（区切り1 で「in-process の 30 秒では起きなかった」のは、たまたま当たらなかったと読む。今回の 60 秒でも 3〜4 回しか起きない）。
- **抜けた瞬間に、録る道具（`pw-record`）のノードの ERR が 7（か 9）ふえる**。抜けているのは「モニターから `pw-record` へ録る道」で、meloet のストリームと出口のノードは、その時 ERR がふえていない。**ヘッドホンに出る音が落ちている印は、ソフトの上にはない**（確かさ B。出口のノードの ERR が全部の落ちを数えるとは限らないので、耳か、出口から入口への線で確かめれば A になる）。
- 2 本の `pw-record` は、ほぼ同じ時刻に抜ける（4 回中 3 回、meloet なしの回は 3 回中 3 回）。録る道具 1 本ずつの都合ではなく、モニターから録る側のノードがまとめて落ちる何かがある。間は 5 秒の倍数に近い（5、10、18、25 秒）。
- `pw-top` の QUANT の欄は、meloet ・ `pw-record` ・ `pw-play` とも 1024、出口は 256（固定の quantum）。meloet の状態行は「バッファ 256」で、コールバックも 256 こまで来ている（鍵 → DAC の数が合う）。

**わからない事**（直していない、調べていない）: `pw-record` のノードが、なぜ 5 秒の倍数くらいの間で xrun になるのか（この PC の PipeWire ・ WirePlumber ・ Chrome のストリームのどれかの都合か、`pw-record` の作りか）。meloet の外の話なので、ここで止めた。測りの道具としては、**出口を `pw-record` で録って「こまが合うか」を見るときは、`pw-record` の ERR を横で見て、ふえた所を外す**のがよい（`click-check.py` に足すのは宿題）。
