# A3 Duplicate a track (round 12)

## Architecture

- **Model** (`crates/meloet-model/src/edit.rs`, next to `add_track_of`): `duplicate_track(doc, track) -> Duplicated { edit, from, track, inserts }`. It clones the whole `Track` (`Track::clone`), so every field comes along, also fields added later (E2 arpeggio, E3 sound knobs). Then it gives new ids, in this order from `Doc::next_id`: the track (the rule of `add_track`: `next_id`, or past the highest track id; now `track_ids`, taken out of `add_track_of`), every clip (the takes stay shared: same `Arc`), every insert (`inserts` keeps old → new), every lane. Lane targets `AutoTarget::Insert { insert }` are moved to the copy's insert (`Duplicated::target`). `Duplicated::folded` turns the source's entries of `Session::folded_lanes` into entries of the copy (the session is not in the `Doc`, so core adds them).
- **Trap for later fields**: a field of `Track` that holds an id, or names an insert or a lane, must get a new id in `duplicate_track`. Everything else is copied by default.
- **Core** (`crates/meloet-core/src/play/tracks.rs`, `play/plugs/copies.rs`): `Play::duplicate_track`. Refused while `busy()` or while another duplicate waits; an id that is no track does nothing; at 64 tracks the notice `TooManyTracks`.
  - With no plugin that sounds on the track, the step is made at once (`make_copy`).
  - With plugins that sound (`Phase::Ready`, no AI state on its way in), each is asked for its state first (`StateAsk::Copy(serial)`, a core-internal ask). When every one has answered, `make_copy` makes the one step from the `Doc` as it is then, with the copy's `PluginRef` states set to what they said. The copies are then loaded the usual way (`PlugState::Bytes` / `Fresh`), so the plugin and the song agree. An answer of `None` (process stopped, plugin gone) or one that comes after a state was put back into the plugin (`Plug::puts` changed) means: the song's state. A plugin the song has "as it starts" whose answer equals its known `base` stays "as it starts" on the copy (with no `base` known that cannot be told, and the copy gets the bytes).
  - The waiting duplicate is forgotten on undo, redo and history jumps (`travel`) and when the song is replaced (`replace_song`). At the end, `busy()`, the track and the 64 tracks are checked again.
- **Why not `PlugState::Of` → `StartState::Of`** (what the spec pointed at; I built that first): the copy's live state then could differ from the song's state for it for ever. Example: a duplicate while the person is in the source plugin's window (a 15-C visit): the source gets its window step when the visit ends, the copy never does. That breaks the rule of the plugin book "once everything settled, every plugin has the song's state" (`Mini::check_states`, `play/plugs/tests.rs`), and redo, the recovery file and an undo back to the copy's first state would give the old sound. Asking first keeps song == plugin always. Cost: the step comes a few ms later (Surge XT says its state in 1.2 ms, 20-3); a plugin that hangs delays it until the stop watcher answers (5 s). Fable advised this way (2nd question).
- **Undo** is the existing delete path: `sync_seats` frees the seat (`ClearSeat`), the plugins are dropped and unloaded in their processes. **Redo** loads the copy with the song's state, which is the state it started from.
- **Selection**: the copy becomes `play_target`, then `selected_track_changed` (so a vocal copy gets its ● by 24-C). Undo of the step leaves the selection to the rule of `after_change` (the first track), as after undoing an added track.
- The copy's plugins go into the process of the same plugin (20-1); processes start one at a time through `launch::spawn` (unchanged `Hosts`). Nothing new on the audio thread.
- Tests: model `edit/duplicate_tests.rs` (fields, ids, `IdBook`, lane targets, independence, undo/redo, names, folded, errors); core `play/tracks/duplicate_tests.rs` (step, seat, engine ops, folded, plugins asked first, "as it starts", no answer, undo/new song while waiting, vocal, 64, recording); `DuplicateTrack` added to the random tests `random_track_edits_undo_and_redo_keep_the_engine_with_the_song` (seats) and `random_plugins_and_presets_with_undo_and_redo_keep_the_engine_with_the_book` (plugins; also during window visits, with `check_states`); real host with fake plugins `service/plug_tests.rs a_duplicated_track_starts_its_plugins_from_the_ones_that_sound`; real Surge XT `surge_xt_a_duplicated_track_sounds_the_same` (`--ignored`).

## Spec rules

For `docs/spec/3-bands.md` ("Rules added in round 12"):

- 「トラックを複製」 is in the right-click menu of a track head, right under 「名前を変える」, with no key. It is not in the menu bar's 「トラック」 menu. Disabled while recording and counting in.
- The copy goes right below the track and is selected. Name: the track's name with the smallest free number from 2 (a number the rule put at its end is replaced: 「ピアノ」 → 「ピアノ 2」, 「ピアノ 2」 → 「ピアノ 3」). Color: the track's.
- Copied: the sound (built-in, SF2, plugin), fader, pan, inserts (built-in and plugins), sends, mute, clips (new ids, the takes shared), automation lanes (moving the copy's own inserts), the folded state of the lanes, the input of a vocal track. Not copied: solo, the ● (record arm), the monitor of a vocal track. A vocal copy gets its ● because it is selected (24-C).
- Plugins start from the state they have now (asked first; the song gets that state in the same step).
- With 64 tracks: 「トラックは 64 本までなので、これ以上足せません。」 on the status line, nothing changes.
- One step 「トラックを複製」. Undo removes the track and its plugins; redo brings them back.
- Keys (`4-keys.md`): none. Step name: `duplicateTrack` 「トラックを複製」 (already in all 6 places).

## Readings

- **Name of the copy**: the base is the track's name without a trailing " N" when N is a number the rule of new tracks makes (digits, 2 or more, no leading 0); then the smallest free number from 2. The copy always has a number, even when the bare base is free. 「リード 1」 → 「リード 1 2」, 「リード 02」 → 「リード 02 2」.
- **Vocal copy and the ●**: the spec says the record arm is not copied and the copy is selected; selecting a vocal track turns its ● on (24-C). I read "not copied" as "the source's ● does not carry over"; the copy gets its ● from being selected (Fable agreed). If the source was armed it stays armed: R then records the same input to both (as when the person selects a second vocal track).
- **Monitor**: not copied (the spec does not say; it is session-only and sounds only with the ●).
- **Mute sets**: the copy is in no set, as any track added later.
- **Plugin state**: asked first, see Architecture (the spec said `PlugState::Of`). A plugin of the track that is still loading, did not load, stopped, or is not on this PC: the copy has the song's state. Values a lane moves while playing are in what the plugin says, so the copy's song state has them (the `Of` way would have done the same).
- **Menu row at 64 tracks**: usable; core answers with the status line (the spec: "the existing limit notice"; there was none, so `TooManyTracks` is new).
- **`TooManyTracks` only for 「トラックを複製」**: the shelf's new track and 「＋ 歌のトラック」 still say nothing at 64, as before (the protocol comment says "and every other way of adding a track"; question for the lead).
- **Wording made up**: `msg.tooManyTracks` 「トラックは 64 本までなので、これ以上足せません。」 (`builder:2026-11-23`, in the words of 「SF2 のファイルではないので、足せません。」), `ui/src/text/ja.ts`, shown by `StatusLine.svelte`. `menu.duplicateTrack` 「トラックを複製」 is the spec's (`user:2026-11-23`).
- **Fake** (`ui/src/bridge/fake.ts` `reduceTracks`): copies the track with new ids (track, clips, inserts, lanes, lane points), not the solo nor the monitor, ● on for a vocal copy; no undo count (as the other track commands there); folded lanes not copied. Scenes `trackDuplicated` and `tooManyTracks` (in `tools/design/shoot_ui.py` with no board).
