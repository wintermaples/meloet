# D2 The AppImage (a trial)

## Architecture

- `scripts/build-appimage.sh` builds in the deb's Ubuntu 24.04 container (`packaging/Dockerfile`,
  same image) with `tauri build --bundles appimage`, passing `meloet-plughost` and `meloet-mcp`
  as `externalBin` like `build-deb.sh`, and `packaging/appimage/tauri.appimage.json` (license
  files into `usr/share/doc/`). `tauri.conf.json` is not changed, so the deb is the same.
- tauri-bundler 2.10.6 (inside @tauri-apps/cli 2.12.6, `src/bundle/linux/appimage/linuxdeploy.rs`)
  downloads AppRun, linuxdeploy and linuxdeploy-plugin-appimage into `~/.cache/tauri` when they
  are missing, the plugin from a "continuous" release, and checks no hash. appimagetool in the
  plugin also downloads the newest "continuous" type 2 runtime. The script downloads all four
  itself, pinned by URL and sha256, puts them where the bundler looks, and gives the runtime by
  `LDAI_RUNTIME_FILE`. linuxdeploy is copied again each time because the bundler writes 3 bytes
  into it (`dd`).
- `LINUXDEPLOY_EXCLUDED_LIBRARIES="libjbig.so*"`: libjbig is GPL-2.0-or-later (only GTK's TIFF
  loader needs it). The script stops if it is found inside.
- Children: `meloet_plugin::launch::spawn` calls `launch::outside_appimage`, which, when
  `APPIMAGE` is set, removes from every variable the `:` entries inside `$APPDIR` (and empty
  entries next to them; a variable left empty goes), and removes `APPIMAGE`, `APPDIR`, `OWD`,
  `ARGV0`, `PYTHONDONTWRITEBYTECODE`, `GTK_THEME` (set by the runtime, AppImageKit's AppRun and
  linuxdeploy-plugin-gtk's hook; read from the real AppDir and `/proc/<pid>/environ`). The same
  for `xdg-open` (`pcwindow.rs`: the file manager and the browser are the PC's programs).
  Outside an AppImage nothing changes (tested). `meloet-plughost` keeps
  `RUNPATH=$ORIGIN/../lib` (set by linuxdeploy) for liblilv, libdbus and their libraries;
  checked in `/proc/<pid>/maps`: Surge XT and ZamComp got the PC's libX11, freetype, GLib,
  libstdc++.
- `meloet --mcp` (`crates/meloet-app/src/mcp.rs`): the first thing in `main`; when the first
  argument is `--mcp`, `exec`s `meloet-mcp` next to `current_exe()` with the rest of the
  arguments (the environment cleaned the same way). Works with the deb too.
- Relative song argument: AppImageKit's AppRun `chdir`s into `$APPDIR/usr` (WebKit's helpers
  are found as `././/lib/...` after the gtk plugin's binary patch), so `meloet song.meloet`
  looked in the wrong folder. `single::full_path` now takes a relative path from `OWD` (the
  folder the runtime was started in) when `APPIMAGE` is set.
- Traps: the gtk plugin copies with `cp --archive`; on the mounted `/work`, keeping root as the
  owner fails with EOVERFLOW for a non-root user and the plugin stops. A `cp` shim in `PATH`
  adds `--no-preserve=ownership`. The container script is one single-quoted string: an
  apostrophe in a comment ends it and the rest runs on the host (it happened once; only a
  `mkdir /work/shim` ran and failed).
- What goes into architecture 23-5: "No AppImage" becomes "AppImage as a trial (round 12, D2):
  `docs/development/appimage.md`".

## Spec rules

- No keys, no wording, no step names.
- `meloet --mcp [args]` runs the AI bridge (the same as `meloet-mcp`).
- An AppImage does not register a menu entry or the `.meloet` file type; a song is opened by
  giving it as the argument.

## Readings

- `GTK_THEME` is removed for children: the gtk hook always sets it (`Adwaita:light` or `:dark`),
  so the PC's own value is gone already; without it the plugin's GTK uses the PC's theme.
- `xdg-open` also gets the cleaned environment ("wherever children are started" in the request).
- `--mcp` is not limited to the AppImage (simpler, harmless for the deb).
- The relative path fix (`OWD`) is new; the spec asks "引数のファイルがひらく", and without it a
  relative path did not open.
- License texts of the runtime's parts were copied into `packaging/appimage/licenses/` from
  the upstream repositories at the pinned tags (type2-runtime dd6cebed, squashfuse 0.5.2,
  libfuse fuse-3.15.0 `LGPL2.txt`, zstd v1.5.6, zlib v1.3.1, mimalloc v2.1.7, musl v1.2.5).
  zstd, zlib, mimalloc and musl are "as packaged in Alpine 3.21"; their exact package versions
  are not known from the runtime's build scripts.
- Not done (request said "STOP rather than ship something unclear", and nothing is shipped):
  the LGPL source offer for the ~170 Ubuntu libraries inside and for libfuse in the runtime,
  and the binary-patched `libwebkit2gtk-4.1.so.0` (`/usr` → `././`, a change to an LGPL
  library). See "Left for later".
- No new wording on the screen.

## Measurements

- AppImage size 98,925,048 bytes (94.3 MiB), sha256
  `c1ae120ab0bf4f1fc851b4af4e998c86f5cf86fc12030e7d533342b3fbd1a7eb` (this worktree, base
  5c0193f plus D2). Build in the container: about 2 minutes with a warm cargo cache.
- Plugin scan from the AppImage on this PC (Wayland, no DISPLAY): 306 bundles in 12.0 s.
- Not measured (the PC was not quiet; the brief forbids it): `tools/measure/latency.sh` with the
  AppImage, key → screen and key → sound, next to the deb's numbers. The tools start
  `target/release/meloet`; they need a way to start the AppImage instead (its `comm` is
  `meloet` too, but it is a grandchild of `dbus-run-session`).

## Left for later

  packages for every package in `usr/share/doc/`, and libfuse 3.15.0 + the runtime's patch)
  from the same place as the AppImage, and decide how to state the binary patch of
  `libwebkit2gtk-4.1.so.0`. The owner decides; the AppImage is not published.
- `tools/measure/*` and `tools/design/shoot_app.py` cannot start an AppImage (they find
  `meloet` as a direct child of `dbus-run-session`). I used `tools/measure/remote.py` with its
  `children` replaced by a deep walk, from a scratch script.
- Not checked: the sound pack download from the AppImage, built-in sounds with the pack, the
  output chooser on first start (a settings file with the output was given), the latency,
  other distributions, AMD/Intel graphics, X11 sessions.
- The AppImage bundles GStreamer core libraries (WebKit needs them) although
  `bundleMediaFramework` is off; no plugins of GStreamer are inside, so media in the page would
  not play (meloet uses none).
- `/var/crash/_usr_bin_meloet-plughost.1000.crash` exists from before (uid 1000, the owner's);
  not from this work.
