# E1 Sounding notes light up in the piano roll

## Architecture

- Core: `Command::SetNoteGlow { on }` is handled like `SetTheme` (`crates/meloet-core/src/state.rs`): the same value does nothing; else `note_glow` changes, `Effect::SaveSettings` (settings.json `"note_glow"`, missing: on) and one `Change::Workspace`. Not a step, not in the song, taken while counting in and recording. The shapes (`WorkspaceView::note_glow`, the setting) were already in protocol 32.
- Which notes sound: `soundingNotes(take, clip, tick, out?)` in `ui/src/components/pianoroll/sounding.ts`, next to `soundingKeys`, by the same rules (a note sounds in [start, start + length); nothing outside [clip.start, clip.end); notes trimmed off the clip's start never sound; nothing while the clip's take is still being fetched). It returns note indexes in index order and writes into a given array. `soundingKeys` is now `keysOf(take, soundingNotes(...))` (same results).
- Where the tick comes from: `frame()` in `Roll.svelte` (the `everyGlFrame` callback that already moved the play line and lit the keyboard column), with `shownTick` (the position reaching the ear). No work in the key path; the glow slot has no `keys: true`, so key events never mark it.
- Per frame, `frame()` fills one kept array (`soundScratch`) and compares it with the last set (`soundNow`) and the take it was for (`soundFor`, the `Shown` of the clip). Only when they differ does it make new arrays: the keys for the keyboard column (`setSounding`, as before) and the lit notes. In a frame where nothing changed it allocates nothing (before E1 `soundingKeys` made a `Set` and an array every frame).
- When notes light: `glowShows` in `ui/src/components/pianoroll/glow.ts`: the setting on, transport `playing` or `recording` (not `countIn`, not `stopped`), not while the clip being recorded is shown (`liveMode`: its notes are drawn as they grow, not the take), not while notes are dragged (`shownDrag`, also until the answer to the drag comes), and the shown clip's track heard (`trackPlays`: not muted, and soloed when any track is; the rule of `Doc::plays`).
- Drawing: one new slot `.glow-box` in the existing `pianoRollLive` region (`.live-host`), before `.live-box` in the page, so drags and the chord shadow draw over it. No new region, no new context (`ui/tests/gl.surface.test.ts` unchanged). The picture is a `LivePicture` painted by the existing `paintLive`: each lit note as `paintNote` (the 2 px gray.10 edge, the face in `trackColor(track)` = `color.track.N`); a drum note as its square. Its places are exactly those of `paintRoll` (a test compares the rectangles).
- The box (`placeGlow`): as tall as the note area (top and bottom from `bind:contentRect` of `.area`, not the rounded `clientHeight`) and as wide as the lit notes, edges on device pixels, moved by `transform: translateX`, its width and height written by hand in `frame()` before the engine measures (so the set and the box change in the same frame). Written only when the numbers change. When nothing is lit the box is 0 × 0 and the canvas goes away.
  - Why full height: the keyboard column canvas (`pianoRollKeys`) and the play line are as tall as the note area and change in the same frames. With the same top and bottom, the piano roll adds one y band with two pieces (the key column, and the glow box which holds the play line). A box only around the lit rows would cut that band into up to 5 bands × 2–3 pieces and pass 10 rectangles in a frame (architecture 7, rule (b)). `alignY` of the engine was not used: it is only for `rects` slots, and it would stretch the drag canvas of the same region too.
  - Why a width limit: on the CPU path a frame whose dirty area is 25 % or more of its bounding rectangle repaints that whole rectangle (with the top band moving, about the whole window). The glow box is full height, so its cost is its width. `glowMaxWidth` = `GLOW_AREA` (0.15) × window area ÷ note-area height (CSS px; about 530 px at 1920 × 1080 with the 588 px note area, about 346 px at 1280 × 800). `glowFit`: when the box of the lit notes is wider, the widest notes are left unlit (the later one first between two as wide) until the rest fit. `glowStep`: when the old box and the new box together are wider, the change takes two frames: first only the notes that stay lit (their box is inside the old one), then the new set. So one frame never repaints more than one limit-wide box for the glow. Example without it: whole-bar chords at the default fit zoom (4 bars over ~1600 px, 400 px a bar) change at the bar line from one 400 px box to the next: 800 × 588 px, over 25 % with the rest of the frame.
  - Re-placing: an `$effect` on the things the box depends on (`glowOn`, `g`, `sizes`, the track color, the limit, `dpr`) marks it stale; the next `frame()` places it again (directly, no two-frame step when the view changed). A page turn (`followScroll`) in `frame()` skips placing in that frame, so the lit notes move in the same frame as the note area's own picture (which its `$effect` draws one frame later).
  - Stopping: the existing `transport.state === "stopped"` effect calls `quiet()` (keys and glow out, the remembered set forgotten so the next play lights again).
- Redrawn only when the set (or the view) changes: the engine draws a region only when its slot's `update` is called and the rectangles differ. A mount test counts the slot's updates over frames.
- Setting: 「表示 ▸ 鳴っている音を光らせる」, a check row at the end of 「表示」 (after 「テーマ ▸」, same group, no new separator), `menus.ts`, sends `setNoteGlow { on: !noteGlow }`. `fake.ts` keeps the setting.
- What a frame dirties (reasoning, not measured): a frame with no change of the set: nothing new. A frame with a change: the old and new glow boxes (one x range around the play line, full note-area height), in the same y band as the key column canvas and the play line, which were dirty in that frame anyway; the status line text 「鳴っている音 …」 changes in those frames as before. So about +0 to +1 rectangle per change frame, and at most `GLOW_AREA` of the window's area for the glow.
- Contrast: `tools/design/contrast-pairs.json` gets `track.1`–`track.5` on `row.white`, `row.black`, `row.out` (kind `ui`, 3:1) and `track.1` against the note faces and accent (kind `note`). All six themes pass (`python3 -I tools/design/contrast.py`: 191 pairs, 0 under).
- Trap: `ui/tests/theme.test.ts` pinned 「テーマ ▸」 as the last row of 「表示」; it now pins it as the row after 「拡大率 ▸」.

## Spec rules

- (Overrides spec 3 「ノートの見た目は変わらない」 while playing, as the round 12 table says.) While playing or recording, the notes of the shown clip that the play line is on are painted in the track's color (`color.track.N`), the 2 px gray.10 left edge kept; on drum rows the hit square. They go back to their own color (velocity gray, or accent when selected) when the line has passed. The keyboard column lights as before.
- Not lit: on a muted track, when another track is soloed (and this one is not), in the count-in, while the clip being recorded is shown, while notes are dragged (until the answer comes), when stopped, and with the setting off.
- Notes whose lit box would be wider than 15 % of the window's area over the note area's height (about 530 px at 1920 × 1080) are not lit, the widest first; a change wider than that together is shown in two frames (the notes that stay lit first, the new ones one frame later).
- 「表示」 menu: 「鳴っている音を光らせる」, a check row, last (after 「テーマ ▸」). On at first; a meloet setting (settings.json), not in the song, not a step; it can be changed while recording.
- The arrange's clips (the spec's second stage) are not lit.
- No new key, no new step name, no new wording besides the menu row.

## Readings

- The look of a lit note: spec 2's note shape with the face in the track color and the 2 px gray.10 edge kept, as a selected note keeps it (the spec's picture fills the whole note; the text only says 「そのトラックの色で塗ります」).
- Drum rows: the square lights while its note sounds (the note's own length, as the drum row names already light), not while the play line is over the square. The spec says nothing of drum rows.
- Mute: only the track's 「ミュート」 and the solo of the session count; a mute automation lane is not read (the spec says 「トラックがミュート」).
- 「再生中（録音中も）」 read as the transport states `playing` and `recording`; not lit in the count-in (the play line waits at the recording's start then).
- While recording into the clip shown, nothing lights: that clip shows the notes being recorded, not its takes. Recording on another track lights the shown clip as playing does.
- Not lit while notes are dragged: the drag shows the original places (gray.7 and accent frames) and the glow would cover them; it also keeps the live canvas to the drag's box. A CC lane drag and the eraser hover do not hide it (Left for later).
- A lit note covers the selection's accent while it sounds (spec: 「そのトラックの色で塗ります」).
- The box is the note area's height, not only the rows of the lit notes (the spec's 「光っているノートを囲む四角」), for the rule of architecture 7 that rectangles changing in the same frame line up their top and bottom (reasons above).
- The width limit and the two-frame change are the 「光らせる数を絞る（同時に32個まで）など」 of the spec's acceptance, chosen by reasoning (and Fable's advice) without measuring: the area of the full-height box is set by its width, not by how many notes are lit, so a cap of 32 notes would not help and was not added.
- The menu row's place (last in 「表示」, with 「拡大率 ▸」 and 「テーマ ▸」) is not in the spec.
- Wording: only 「鳴っている音を光らせる」 (`menu.noteGlow`, `user:2026-11-23`). Nothing made up.
- Fake scenes: `pianoRollGlow` (F-PRPlay's song playing at 1.3.240: C3 G3 C5 lit; E4 and G4 have just ended), `pianoRollGlowMenu` (the same with 「表示」 open, the row checked). `pianoRollPlay` (F-PRPlay) now shows C3 E3 G3 C4 lit too (the rule E1 overrides); `drumPlay` shows the snare and closed hi-hat squares lit. Shot in all 6 themes.

## Measurements

None (the PC was not quiet). To measure after the merge, on a quiet PC, after `tools/measure/build-dev.sh`:

- Songs: `python3 -I tools/measure/make_song.py /tmp/e1-10k.meloet --notes 10000 --bars 64 --tempo 96` (like the scene `pianoRoll10kPlay`: the set changes almost every frame), and a song of whole-bar chords (4 bars of 3–4 note chords, one a bar; write it in meloet with the grid at 1 bar and the chord stamp, or with the AI link, and save it) for wide lit boxes.
- `tools/measure/webkit-damage.sh --song <song> --commands '{"afterMs":1800,"command":{"type":"selectClip","clip":2}},{"afterMs":2000,"command":{"type":"toggleBand","band":"pianoRoll"}},{"afterMs":2600,"command":{"type":"playStop"}}'` with each song (the clip id of a hand-made song may differ). Expected: no frame repaints the note area whole; at most 10 rectangles a frame; no "one rectangle around all" at the bar lines of the chord song. If there is: lower `GLOW_AREA` in `glow.ts`.
- busyMs on and off: `tools/measure/app-watch.sh --song /tmp/e1-10k.meloet --seconds 30 --commands '<the three above>'`, and the same with `{"afterMs":1600,"command":{"type":"setNoteGlow","on":false}},` added in front (each run starts with a fresh settings folder, so the glow is on at first). Acceptance: p95 busyMs differs by 1 ms or less.
- Key → screen: `tools/measure/latency.sh --pattern mixed --piano-roll --state playing`, and the same with `--commands '{"afterMs":3000,"command":{"type":"setNoteGlow","on":false}}'`; compare with each other and with the last numbers in `docs/measurements/`. Also `tools/measure/latency.sh --pattern mixed --piano-roll` (stopped).
- `tools/measure/ui-script.sh --song /tmp/e1-10k.meloet --script pr-scroll:100` while stopped should not change (nothing is lit when stopped).
