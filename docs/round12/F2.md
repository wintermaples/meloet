# F2: mp3 export and the song's information (round 12)

Spec: `docs/history/round12-spec.ja.html` F2 (lines 737-758). Protocol 32 shapes were already in; no shape was added.

**Outcome: mp3 did not meet its acceptance conditions and stays hidden.** Item 2 of the conditions ("at 192 kbps the difference is 20 dB or more below the source, for a 1 kHz tone and pink noise") fails for pink noise: −14.4 dB at 44100 Hz and −13.4 dB at 48000 Hz. LAME 3.101 fails the same rule on the same signal (−13.7 and −12.8 dB). Items 1 and 3 pass. As the spec says (line 757), the song's information (lofty) stays for wav and flac, and mp3 is not in the list of formats. The mp3 work is kept apart, whole and tested, as a patch (see "Left for later"), so it can come back if the owner changes the rule.

## Architecture

What goes into chapter 25 of `docs/architecture.md`.

- **「曲の情報」 in the rules** (`crates/meloet-core/src/export.rs`). `Exporting` keeps the title as typed (`None`: the song's name), the picture (`tags::ExportPicture`: its file name, png or jpeg, the bytes), and the folder the last picture came from. The title and the picture belong to the song they were chosen for: when the dialog opens for another song (`Play::serial` changed) they go back to the song's name and no picture. The artist is a setting (`export_artist`, already in settings version 1): `ExportChange::Artist` changes it and `state/export.rs` sends `Effect::SaveSettings` when it changed. 「書き出す」 puts all three into `ExportTarget::info` (`tags::SongInfo`); for wav the picture is left out (the row is shown, `picture_usable` false).
- **Choosing the picture**: `ExportChange::ChoosePicture` (not for wav, one window at a time) → `ExportAsk::PickPicture { folder }` → `ShellRequest::PickExportPicture` → `pcwindow::Pick::Picture` (GTK `FileChooserNative`, title 「ひらく」, filter `*.png *.jpg *.jpeg` in either case) → `Core::export_picture_picked(path)`, which reads the file on a short thread of its own (`meloet-picture`; never the core thread nor the GTK main thread) with `tags::read_picture` → `ExportNews::PicturePicked(Some((path, Ok(picture) | Err(problem))))`. The rules take it only while they wait for it. A problem becomes `StatusMessage::ExportPictureTooLarge` / `ExportPictureUnreadable` (the file name only; the path is never sent to the screen); `Model::status` shows these two over the open export dialog (otherwise the dialog's own line wins), and the next command clears them, as any notice.
- **Reading the picture** (`tags::read_picture`): at most `EXPORT_PICTURE_MAX_BYTES + 1` bytes are read (`Read::take`), so a file that grows while it is read is still too large. png or jpeg is decided by the bytes, not the ending, with lofty's header readers (`PictureInformation::from_png` / `from_jpeg`: the png signature and IHDR, the jpeg SOF marker). The picture is not decoded.
- **Writing the information** (`crates/meloet-core/src/export/tags.rs`, lofty 0.25.5): in the job (`export/job.rs` `go`), right after `convert()` has written a file into the work place and before it is moved, so a half-tagged file is never where the person looks. For 「トラックごと」 each file's title is `SongInfo::for_track`: 「題名 - トラックの名前」 (only the track's name when the title is empty). Empty text is not written; nothing at all is written when there is nothing to say.
  - flac: lofty's generic `Tag` of `VorbisComments` with the picture as a PICTURE block, `save_to_path` (lofty moves the audio with 64 KiB copies; it does not read the file into memory).
  - wav: a RIFF `LIST INFO` chunk (`INAM`, `IART`). lofty makes the bytes (`Tag::dump_to`), and `tags::append_riff_info` puts them after the data and grows the RIFF size: lofty's own wav writer reads the whole file into memory (`iff/wav/tag/write.rs` `read_to_end`), which for a long 32-bit export is hundreds of MB. A wav whose RIFF size does not match the file, or would pass `u32::MAX`, gets no list.
  - An error while writing the information is an error of the export (`ExportFailure::CannotWrite`), as any other write.
- **The AI link's exports** write no information (`state/ai.rs`: `SongInfo::default()`); its tool is unchanged.
- **New text for architecture 22-11**, in place of "mp3 is not offered (the owner's decision). The only non-LGPL encoder (`rusty_mp3` 1.1.0) was new and unproven.": "**mp3 is not offered.** Round 12 F2 built it with `rusty_mp3` 1.2.2 (Apache-2.0, pure Rust) on the owner's condition that it meets the acceptance conditions of the round 12 spec; it did not (at 192 kbps pink noise comes back 14.4 / 13.4 dB below the source, the rule asks 20 dB; LAME 3.101 gives 13.7 / 12.8 dB on the same signal). The work is kept on a side branch (docs/round12/F2.md). **Song information**: after a file is brought into its form in the work place and before it is moved, `export/tags.rs` writes the title, the artist and the picture with lofty 0.25.5: Vorbis comments and a PICTURE block in flac, a RIFF `LIST INFO` (`INAM`, `IART`) after the data of a wav (lofty makes the bytes; meloet appends them, because lofty's wav writer reads the whole file into memory). 「トラックごと」: 「題名 - トラックの名前」. The AI link's files have none."
- **mp3 stays a stub** (`// round12 stub: F2` in `export.rs`, `sink.rs`, `ui/src/bridge/fake.ts`): not in `formats`, `Format { Mp3 }` and `Mp3Kbps` do nothing, `mp3_kbps_choices` empty, `Done::mp3_kbps` `None`, the sink refuses mp3.
- **Traps met**:
  - lofty 0.25.5 does not build with `default-features = false` (`id3/v2/frame/read.rs` names `Id3v2Error` behind the `id3v2_compression_support` feature). It is used with its default feature, which brings flate2 (MIT/Apache-2.0, with crc32fast, miniz_oxide, adler2, simd-adler32).
  - `Model::with_export_dirs` made a new `Exporting` and so dropped the artist read from the settings (the real app calls it after `Model::new`); it now keeps the artist.
  - symphonia 0.6.1 without its `id3v2` feature (meloet's features: flac, wav, pcm, mp3, ogg, vorbis) does not read an ID3v2 tag at the head of an mp3: its probe looks for the first frame byte by byte for at most 1 MB (`FormatOptions` `max_probe_depth`, `symphonia-core/src/formats/probe.rs`). An mp3 with a large picture in its tag does not open, and bytes inside a picture that look like a frame head can be taken for one. The mp3 patch turns `id3v2` on (tested with a 4.9 MB picture). Without the patch it matters only for mp3 files people bring in (see "Left for later").
  - symphonia's `Metadata::pop` never takes the last revision out of the log; the current one is `Metadata::current` (what the tests read).

**The mp3 layer (in the patch, not in this tree).** For the record and for whoever applies it:
- `rusty_mp3` `=1.2.2` (Apache-2.0, no dependencies, published 2026-11-23; LICENSE file read: the full Apache-2.0 text, "Copyright 2026 Mata Network"). `export/sink.rs` `Mp3Sink`: `Mp3Encoder::new(Mp3EncoderConfig { bitrate_kbps, vbr_quality: None })`, `push_pcm_f32(&interleaved, channels, rate)` with every sample put within ±1 first (non-finite → 0; the crate itself lets up to 8× full scale through, `MAX_INPUT_AMPLITUDE`), no dither; frames written as `next_packet` gives them (until `Again` / `Eof`); at the end `finish()`, the rest drained, and `lame_tag_frame()` written over the first frame (the Info tag: delay 528 + 529 and padding, which symphonia and ffmpeg use to play exactly the samples given; it is checked to be as long as the first frame). A sink that got nothing still pushes an empty slice so the file is whole. `SinkSpec::mp3_kbps` and `ExportTarget::mp3_kbps` carry the bitrate.
- Rules: `formats` = wav, flac, mp3; `mp3_kbps` (192 at first, one of `EXPORT_MP3_KBPS`, kept while meloet runs); for mp3 the sample rates are `EXPORT_MP3_SAMPLE_RATES`, and a rate chosen for the others (or the engine's) becomes the one of its family (`rate % 11025 == 0` → 44100, else 48000); choosing mp3 keeps the bits chosen for wav and flac (bits mean nothing to mp3); `Done::mp3_kbps` is the bitrate. The engine renders stereo, so an mp3 is always stereo. The `rusty_mp3` crate gets `opt-level = 3` in the dev profile.
- In `rusty_mp3` 1.2.2 (read in `~/.cargo/registry/src/…/rusty_mp3-1.2.2/src/lib.rs`, `encode/mod.rs`, `encode/lametag.rs`): for CBR up to 256 kbps at 32/44.1/48 kHz it keeps every frame's coded data in memory until `finish()` (the bit reservoir is laid out at the end; about the size of the file, 14 MB for 10 minutes at 192 kbps), and hands out no frame before; 320 kbps does not use the reservoir. The encoder string in the tag is `LAMErusty`, which symphonia's mp3 reader accepts (it reads the delay only for `LAME`, `Lavf`, `Lavc`).

## Spec rules

For `docs/spec/3-bands.md` "Rules added in round 12", the export dialog (34-B):

- 「くわしく」 has 「曲の情報」 after 「実時間で書き出す」: 「題名」 (a box; at first the song's name), 「作者」 (a box; kept with the PC's settings), 「絵」 (the picture's file name or 「なし」, 「はずす」 while there is one, 「えらぶ…」).
- What is typed in 「題名」 or 「作者」 is taken when Enter is pressed or the box is left; Esc puts back what was there. Enter while the input method is composing is the input method's.
- 「えらぶ…」 opens the PC's open window (「ひらく」) for a png or a jpg of at most 5 MB (5 MiB). A picture that is too large or does not read as png or jpg is not taken, and the status line says so over the dialog: 「「表紙.png」は大きすぎるので使えません（絵は 5 MB まで）。」, 「「表紙.bmp」は絵として読めません（使えるのは png ・ jpg）。」.
- A wav holds no picture: for wav the row 「絵」 is shown and cannot be used (a picture chosen for flac stays chosen and is not written into the wav).
- The title and the picture belong to the song: opening another song puts the title back to its name and takes the picture away.
- The file holds the title and the artist (wav: RIFF INFO), and the picture (flac). 「トラックごと」 titles each file 「題名 - トラックの名前」.
- mp3 is not offered (spec 3: 「使えないとき mp3 は出さない」): it did not meet the conditions of round 12 F2.
- No keys, no step names (nothing of the song changes).
- New text for `docs/spec/7-readings.md` C-11 (the row "mp3 in export"): "Not shown. Round 12 F2 built mp3 with rusty_mp3 1.2.2 on the owner's condition (2026-11-23: offered only if it meets the acceptance conditions of F2). It did not: at 192 kbps pink noise comes back 14.4 dB (44100 Hz) and 13.4 dB (48000 Hz) below the source, the rule asks 20 dB (LAME 3.101 gives 13.7 and 12.8 dB on the same signal). The mp3 work is kept on the side (docs/round12/F2.md). The song's information of F2 is offered for wav and flac. Read mp3 in the format lists of F8-ExportCheck, F8-ExportClip and R12-Fit the same way." Source: the owner's decision (C-11) and `user:2026-11-23`.

- Where: the three rows are in 「くわしく」 after 「実時間で書き出す」, under the small heading 「曲の情報」 (gray.8, as the labels of the dialog), each a row of the same form as the others (name 120 wide); the boxes use the input box of the key list (`part.input.height`, gray.0 with a gray.6 line, gray.8 when focused). 「はずす」 comes before 「えらぶ…」. The spec has no mock for F2.
- The title belongs to the song (kept while the same song is open, also when the dialog is closed and opened again); the spec says only "at first the song's name". An empty title writes no title.
- The picture is kept with the title (per song); "5 MB" is `EXPORT_PICTURE_MAX_BYTES`, 5 MiB.
- The window for the picture starts in the folder of the last picture chosen, else the song's folder, else the home folder.
- png or jpg is decided by the file's bytes (a `.PNG` that holds a jpeg is taken as a jpeg); the picture is not decoded, only its head is read.
- The artist is saved in the settings as soon as it changes, even if the export is then cancelled (it is a setting, like the others in the dialog that are not).
- The AI link's exports write no song information.
- wav: RIFF INFO after the audio data (as lofty itself puts it when there is none). ffmpeg and lofty read it there; symphonia does not (it reads INFO only before the data).
- Spec says "wav は RIFF INFO（題名と作者だけ）": only `INAM` and `IART` are written.

## Measurements

The PC was not quiet (other helpers were building); numbers of speed are only rough.

**Acceptance conditions of mp3 (run with the patch, `crates/meloet-core/src/export/mp3_gate_tests.rs`; decoded with symphonia 0.6.1 as meloet reads audio; residual = 10·log10(Σ(decoded − source)² / Σ source²), both channels, sample-aligned by the Info tag):**

1. Length of a real song export (the export tests' song: synth lead, electronic kit, three vocal clips, delay, reverb, tempo ramp; 6 bars; 192 kbps): 44100 Hz 600498 frames → 600498; 48000 Hz 653603 → 653603 (exact; the rule allows ±1152). Every frame walked from the first byte to the last: MPEG-1 Layer III, the bitrate and rate asked for, the Info tag first, nothing after the last frame. Residual of this song: −27.0 dB (44100), −25.1 dB (48000). **Pass.**
2. Residual at 192 kbps, 10 s signals: 1 kHz tone at −6 dBFS: −63.6 dB (44100), −64.4 dB (48000) **pass**; pink noise (Paul Kellet's filter, −15 dBFS RMS, a channel of its own each side): −14.4 dB / −13.4 dB **fail** (needs −20); the same pink noise on both sides: −14.4 / −13.4 **fail** (rusty_mp3 gains nothing when left = right).
   - All bitrates, pink noise (44100 / 48000): 128 kbps −10.1 / −9.5, 192 −14.4 / −13.4, 256 −18.1 / −17.0, 320 −21.8 / −20.4. 1 kHz: −59.3 / −61.6 … −70.7 / −72.3.
   - By band (192 kbps, pink, 44100): 0–4 kHz −19.1, 4–8 −10.4, 8–12 −9.0, 12–14 −8.3, 14–16 −7.9, 16–18 −6.7, 18–20 −6.3, 20–22 −5.6 dB: the difference is spread over the whole band, not a low-pass cut.
   - The same signals through LAME 3.101 (`lame --cbr -b 192`, ignored test `the_same_signals_through_lame`, needs `/usr/bin/lame`): pink −13.7 / −12.8 dB, pink left = right −16.3 / −14.9, 1 kHz −30.5 / −30.4; `-b 320`: pink −18.3 / −16.4, 1 kHz −70.5 / −66.1. LAME cuts above about 18–19 kHz at 192 kbps (those bands come back at 0 dB).
   - Fable (asked during the work, confidence C, its own estimate): at 96 kbps a channel, 44.1 kHz, about 2.18 bits a sample, so about 13 dB plus about 4 dB from the 1/f shape: an encoder of any kind can hardly reach 20 dB on independent pink noise at 192 kbps; the measured numbers are about 3 dB under that.
3. Silence (3 s), one sample, nothing at all, full-scale square, 4× full scale with NaN and ±infinity: at both rates, all four bitrates, mono and stereo, every file is whole frame by frame, reads back exactly as long, finite and within ±1.5 (silence within 1e-4). Ten minutes of a song-like signal (chords, bass, clicks, noise; 48000 Hz, 192 kbps): whole, exactly as long, residual −25.3 dB; 5.35 s to write in a debug build (rusty_mp3 at opt-level 3), 14,401,152 bytes. 「やめる」 while the job brings the song into mp3: the work folder is removed and the file is either not there or whole; a sink given up removes its file. The same audio in pieces of 1, 333, 4096 frames or all at once gives the same bytes. **Pass.**
4. Files for the ear (with the patch; ignored test `files_for_the_ear`): `target/r12-f2-ear/test-song-192k.mp3`, `test-song-320k.mp3` and `test-song-24bit.wav` (the export tests' song with its tail, 48000 Hz, 15.7 s, title "F2 test song", artist "meloet"). ffprobe reads the same length for the three (15.718 s) and the tags; `ffmpeg -v error -i … -f null -` decodes them without an error.
- mp3 tags (patch): lofty and symphonia read back the title, the artist and the picture, also with a 4.9 MB picture; the frames and the length are as before.

For the lead after the merge: `tools/measure/export_app.py same` (unchanged path for wav and flac when there is no information; with the default title, the file now has a tag) and `export_app.py speed` (one more step at the end: flac moves its audio to make room for the tags and the picture).

## Left for later

- **The mp3 work** is a patch on top of this tree: `target/r12-f2-mp3/F2-mp3.patch` in this helper's worktree (27 files: the rusty_mp3 dependency, NOTICE and the about list, `Mp3Sink`, the rules offering mp3, the screen's 「ビットレート」 row and the bitrate in 「書き出しました」 and in the status line, the fake and two scenes `exportMp3` and `exportDoneMp3`, the AI link's message, symphonia `id3v2`, and the tests: `mp3_gate_tests.rs` with the failing item 2, `mp3_tests.rs`, `ui/tests/export.mp3.test.ts`). `git apply --check` passes on this tree; with it applied, everything passes but `gate_two_…`. It should go on a side branch before the worktree is cleaned up. Whether the rule of item 2 changes is the owner's question.
- Without the patch, meloet cannot open an mp3 someone brings in whose ID3v2 tag is larger than 1 MB (a large cover picture), and a picture in a smaller tag can be mistaken for audio frames: symphonia's `id3v2` feature is off (pre-existing; the patch turns it on, and it could be turned on alone).
- rusty_mp3 1.2.2 reads environment variables in a normal build (`MP3_RESERVOIR`, `MP3_RESV_GAIN`, `MP3_RESV_LOOKAHEAD`, `MP3_STEREO`, `MP3_PICK`, `MP3_SHAPE`, `MP3_PSY_DOMAIN`, `MP3_SHORT_SHAPE`, `MP3_THR_CAP`, `MP3_SMR_DB`, `RFF_MP3_XRPOW`): a person's environment could change the files. Its own notes name a known bug when the stereo mode switches nearly every frame (`encode/mod.rs` `decide_stereo`), and the reservoir is off at 320 kbps because it garbled frames there.
- The title and the artist have no length limit.
- `crates/meloet-ai` test `track_ids::lists_take_numbers_and_ids_together` failed once while the meloet-app tests ran at the same time, and passed 3 times alone (timing under load; not touched by F2).
- Not checked by hand in the real app: the PC's window for the picture (GTK filter, title), typing Japanese with the input method in 「題名」, the status line under the dialog.
