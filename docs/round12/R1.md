# R1 Keep what was just played (round 12)

## Architecture

**The engine says every key, always** (`crates/meloet-engine/src/engine.rs`, `clock.rs`).

- The transport counts **runs** (`Transport::run`): a new run begins whenever the play starts, stops or jumps (`Play`, `Stop`, `Locate` while moving, `Record`, `RecordHere`), when the loop changes while playing (`SetLoop` with other values), and when a moving transport is stopped by `prepare` (a new stream). `Transport::run_lap` counts how often the loop went round in a run that plays (`step_at`). Both are written into every clock segment (`Segment::run`, `run_lap`; the segment has 11 words now) and come out of `HeardPosition` (`run`, `run_lap`).
- `Recorded` has two new kinds in the same ring as the recording's items:
  - `Recent { event, t_us, run, at }`: a keyboard event taken while the transport is stopped or plays. `at` is `Some(RecentAt { tick, lap })` in a run that plays (the position that reached the ear at `t_us`, found in the clock exactly as `stamp` does for a recording), `None` in a run that stands still.
  - `RecentEnd { run, t_us, at }`: the run ended. `at` is where the listener was then (a run that played), so held keys can be cut there.
- Which run a key belongs to is decided by **the order the engine reads things in**, not by the time the sound reaches the DAC: a key read after the engine took `Play` belongs to the playing run even when its first frame is not heard yet. Its position is then counted back from the frames about to be rendered (`run_place` falls back to `segment_now(0, timing)`), so it lands just before where the play starts. Only a stop splits by time: keys with `t_us` after the stop's own time go to the run the stop begins (`after_stop` in `stamp_played`), and are pushed before that stop's `RecentEnd`.
- Nothing is said while counting in or recording: those keys are the recording's (`stamp`).
- **Ring headroom** (`RECORDED_HEADROOM` = 256 of 4096): `Recent` is dropped (and `record_overflows` counted) while fewer slots are free, so a core thread that does not read for a long time can never make the ring lose a recording's `Started` or `Stopped`. `RecentEnd` is pushed like the recording's items.
- Audio thread: no allocation, no lock (`rtrb` `Producer::slots` is two atomic loads; one `segment_at` per key while playing, as `stamp` does). `every_transport_path_stays_off_the_allocator` now also checks that both kinds of `Recent` went through it.

**The core keeps one phrase** (`crates/meloet-core/src/play/recent.rs`; rules at the top of the file).

- `service.rs` `poll_engine` turns the ring's `Recent`/`RecentEnd` into `Played` items and hands them over **in batches** (`Input::Played { items, held }`), one `handle` per batch, flushed before any other report so the order is kept. One `handle` per key would rebuild the view for every controller move.
- `Recent` (in `Play`): at most one `Phrase` (run, playing or not, the keys target track, the loop it went round, the controller values before its first event, up to 4096 events, when and where its run ended), plus which keys and controllers are held now and since when nothing is held.
- State rules: an event of the phrase's run is added; an event of another run or `RunEnded` of its run closes the phrase; a closed phrase stays until the next **key press**, which starts a new phrase in its place; anything else with no open phrase is dropped (the controller values are still followed, for the head of the next phrase). In a run that stands still, a key press after no key and no pedal (CC 64 ≥ 64) was held for the time of two bars (tempo and meter at the play line) starts a new phrase too.
- Limits: over 4096 events the oldest key press goes with what followed it up to the next press (controller values dropped that way move into the phrase's head). With only one press left (a held key under a flood of controller moves) the oldest move after it goes instead. Events more than 10 minutes older than the newest go the same way.
- Forgotten: after it was kept, when a recording ends (`RecordReport::Stopped`, `stream_gone` with a recording), when the keys target changes (`selected_track_changed`, `after_change`, and checked again in `take`, `can_keep_played` and `keep_played`), when the song is replaced.
- **What is held is read anew after a gap** (`HeldNow`, `Recent::lost_track`): keys a recording took, or keys played with no stream, never come as `Played`. Each batch carries what the MIDI thread knows is held (`Held::now`); the core takes it over at the first batch after a recording ended or a stream opened. Without it a pedal let go during a recording would stay "down" in the core for ever (no phrase would ever rest, and the next take would start with the pedal down).
- `Play::keep_played`: refused while `busy()` and with no keys target; with no key press `StatusMessage::NothingToKeep`. Otherwise the phrase is placed (`Phrase::place`), fed to the model's `Recorder` (`new / push / finish`), and put in with `edit::add_recording`, or with 「重ねる」 on by `overdub_recording` for each take on top of the one before, as `finish` of a recording does. The step's `StepKind::Record` is renamed `StepKind::KeepPlayed`; `apply_selecting` makes the one step and selects the clip. No engine command for the transport is sent.
  - Played while the song played: events at their heard ticks and laps. The recorder starts at the head of the bar of the first event; with a loop each time round is a take.
  - Played while it stood still: the first key goes to the head of the bar of the play line (`play_line()`, so the heard position if the song plays now); every other event at `(t_us − first t_us) ×` the tempo at the play line.
  - Held keys are let go where the phrase ends: where its run ended (`RunEnded`), or for an open phrase now (the heard position of the same run from `HeardRun`, or `now_us`). When that is not known (the run ended with the stream, the heard run is another one) the phrase ends at its last event.
  - The clip ends on the bar line at or after the end (and past the last event of its last pass).
- The service reads the ring once more before it handles `Command::KeepPlayed`, so keys of the last 100 ms (the poll rate while stopped) are kept too. `handle_now` gives the model the heard run with each input (`Model::set_heard_run`, read from the same clock answer as `Heard`).

**The seam for R2 (typed keys) and E2 (arpeggio).**

- Engine: every played event enters through `Engine::key_in(midi, timing, record_until)` (it sounds on the play target) and then `Engine::stamp_played` (it is written down for the recording or as `Recent`). A second source of notes must come through these with a `MidiIn { event, t_us }`. The MIDI ring has one producer (the MIDI thread owns `MidiFeed`): R2 must not push into it from the core thread. Either give the typed key to the MIDI thread, which already is the one place that applies fixed velocity, `Held` and the screen's key lights (`play_key` in `service.rs`), or bring it in as an `EngineCommand` that calls `key_in`.
- E2: "the notes that really sounded" means the arpeggio's notes call `stamp_played` (not `key_in`'s instrument call for the held keys), with the time each note is heard. `stamp_played` needs a `t_us`; for a note made at a frame of the block that is `dac_us(frame, timing)`.
- Core: `Played::Key` does not say where a note came from; `recent.rs` needs no change for a second source. `HeldNow` comes from `Shared::held`; typed keys must be in it (they are if they go through `play_key`).

**Traps.**

- `Recorded` readers that expect only a recording's items must skip `Recent`/`RecentEnd` (a `RecentEnd` now comes before `Started`): done in the engine test rigs and `tests/plugin_hosts.rs`.
- `HeardPosition::lap` is still the recording's lap and was left alone (the core's overdub and automation read it); the play's lap is `run_lap`.
- The core closes nothing by itself: the engine's `RecentEnd` is the only close, so the two can not disagree about where a run ended.

## Spec rules

For `docs/spec/3-bands.md` ("Rules added in round 12"):

- 「さっきのを残す」 is in the top band right of 「重ねる」. Disabled while there is nothing to keep, lit (accent) while there is. Menu 「再生 ▸ さっきの演奏を残す」 below 「録音」 (disabled the same way). Key Shift R.
- What is kept: the keys, CC and pitch bend (after fixed velocity) played on the keys target track while not recording and not counting in, as one phrase from a key press on.
- A start or stop of the play closes the phrase; the next key press after that starts a new one and the old one is gone. So does a jump of the play line while playing and a change of the loop while playing. While stopped, a key press after no key and no pedal was held for the time of two bars (at the tempo and meter of the play line) starts a new phrase.
- Gone: after it was kept, when a recording ends, when the keys go to another track, when another song is opened or made. At most 4096 events and 10 minutes; the oldest go first.
- Kept while played along with the song: at the positions heard, each time round the loop a take. Kept from a stopped song: the first key at the head of the bar of the play line, the rest by the time that passed at the tempo there. No quantizing. The clip runs from a bar line to a bar line; keys still down end where the play stopped, or at the moment of keeping.
- Put in as a recording is (clips there are merged; with 「重ねる」 on, into the shown take). One step 「さっきの演奏を残す」; the clip is selected; the play does not start or stop.
- Refused (nothing happens) while counting in or recording and with no keys track as the target. With no note: status line 「残せる演奏がありません」.
- The button is the first thing of the top band to hide when the window is narrow: it shows only when everything else (the keys on the buttons, the song name, 「処理の負荷」, the count-in, the position labels, 「重ねる」) is shown in full. While hidden, Shift R and the menu row still work.

`docs/spec/4-keys.md`: Shift R 「さっきのを残す」 (not while typing). Step name `keepPlayed` 「さっきの演奏を残す」 (was already in all 6 places; history row 「テイク N」 as for a recording).

## Readings

- **Runs that end without a play/stop switch**: a `Locate` while playing, `Play` while playing, and a change of the loop while playing also close the phrase (the spec names only play ↔ stop). Reason: a phrase has one line of positions and one loop for its laps; after a jump or another loop the recorder's rules do not hold.
- **Which run a key near a start belongs to**: by the order the engine reads (see Architecture). A key pressed in the few ms between the play command and its first heard frame is placed just before the start, like a pickup in a count-in.
- **Keys after a stop is asked** (read in the same block as the stop): they belong to the stopped run, so as a key press they start a new phrase and the played one is gone. This is the spec's rule ("a new note-on after closing"), noted because the window is only a block wide.
- **Pedal for "nothing held"**: only CC 64 (≥ 64 is down). The time of two bars uses the tempo and the meter at the play line when the key arrives.
- **A phrase starts at a key press**: controller events before the first press are not events of the phrase, but their values are written at the head of the take (as a recording does with `HeldControls`), so a pedal pressed before the first chord still holds it.
- **Overflow**: dropping "from the old side" drops whole notes (a press with what followed it), so the phrase always starts with a key press; with one press left the oldest controller moves go instead.
- **The end of the clip**: the bar line at or after the end position (a phrase kept exactly on a bar line does not get an empty bar).
- **Overdub**: read when 「さっきのを残す」 is pressed (not when the keys were played).
- **Keyboard pulled out / MIDI stopped**: the keys and the pedal held in the phrase are let go at that moment (as a recording's keys are).
- **The button's look**: lit (`.m-btn.on`) while something can be kept, from the spec's picture; `aria-disabled` otherwise. No key shown on the button (as 「重ねる」). A click while disabled sends nothing; Shift R always sends, so the status line can say 「残せる演奏がありません」.
- **Where it hides** (decided by the lead on 2026-11-24; the spec says nothing): the button is the first thing hidden (`transportWithKeep` in `ui/src/components/fit.ts`), because a new control must not push out parts the spec and the mocks already show (the same decision as for P2). At 1280 × 800 the top band is the same as before R1, pixel for pixel (scenes `tracks6` at 100 % and 150 % and `pianoRoll` at 100 %, against shots of the base commit `5460482`); at 1920 × 1080 the button shows. **Question for the owner: at 1280 px wide the button is hidden (the feature is reached by Shift R and 「再生 ▸ さっきの演奏を残す」); is that right?**
- **Not built: the picture's status line** 「さっき弾いた 2 小節ぶん（ノート 14）を残せます」. The text of the spec does not ask for it and the protocol has no shape for the bars and the note count (`can_keep_played` is a bool that must not change with every key).
- **Wording** (`ui/src/text/ja.ts`, all `user:2026-11-23`, taken from the spec): `transport.keepPlayed` 「さっきのを残す」, `menu.keepPlayed` 「さっきの演奏を残す」, `msg.nothingToKeep` 「残せる演奏がありません」. The key list row reuses `keyList.keepLast` / `key.keepLast` of G1. Nothing made up.

- **`tools/measure/record-timing.sh`**: `private` runs only the recorded runs (as before in time); the new mode `keep` runs the same matrix with play + 「さっきのを残す」 and writes under `keep/`.
- **Fake** (`ui/src/bridge/fakeRound10.ts`): with `canKeepPlayed` it puts a clip of two bars with 4 notes at the bar of the play line on the keys track (only where no clip is in the way; Rust merges), selects it and makes the history row; else `nothingToKeep`. ## Measurements

No latency or speed was measured (the PC was not quiet: load average 13 to 25, other helpers building).

One short run of the new position test, for correctness only (`MELOET_TIMING_QUANTA=256`, private PipeWire, debug build, loaded PC, 2026-11-25 00:33): on the runs the load left alone, kept keys landed like recorded ones (kept 96 bpm: mean +0.045 ms, max 0.199 ms; recorded 96 bpm: mean +0.035 ms, max 0.188 ms). Both the old recorded test and the new kept test failed their per-key bound on other runs of the same session, with the test's own sender up to 9.5 ms late, so the numbers are not a result.

**The lead must measure on a quiet PC** (spec 1-4: the input and the audio thread were touched):

- `tools/measure/latency.sh --state stopped|playing|recording` (the audio thread now pushes one item per key while stopped and playing, and looks the position up while playing).
- `tools/measure/record-timing.sh private` (the recording path; segments grew by one word).
- `tools/measure/record-timing.sh keep` (new: positions of kept keys at quantum 64 to 1024, two tempos, on time and 5 ms late, and the changing timeline). Expect the same range as `private`.
