# R2: play with the PC keyboard (「キーで弾く」)

## Architecture

What goes into chapter 25 of `docs/architecture.md`.

**The way of one key** (screen → core thread → engine; the same as a MIDI key from `play_key` on).

- **Screen** (`ui/src/keys/typed.svelte.ts`, called first in `handleKeydown` of `attach.ts`, before the lane and timeline keys and before the 「音が出ました」 hint is put away): while `keyboards.typedKeys` and no text is typed, a key without Ctrl, Meta, Alt or Shift is the PC keyboard's when its `KeyboardEvent.code` is a note key (`TYPED_NOTES`), Z, X, or any other letter or digit (`Key[A-Z]`, `Digit0-9`, `Numpad0-9`). Such a key is never a shortcut: its default is prevented and it returns. Repeats (`ev.repeat`) are dropped; a key already held is not sent again. The note goes out with `post` (below) as `typedKey {note, down, tUs}`; the held keys are kept by code with the note each one sounds, so keyup lets go of exactly that note whatever the octave is now. `handleKeyup` (now given the deps) lets go of a held key even while typing.
- **The time** (`tUs`): `KeyboardEvent.timeStamp` turned into Rust's CLOCK_MONOTONIC with `clockOffsetUs()` (the shortest of 5 round trips of `clock`, as the play line does). The offset is asked once, at the first key; until it is there `tUs` is 0. A time more than 1 s away from `performance.now()` is taken as now (in case an event time is not on that clock). 0 means "now" to Rust.
- **Not waiting** (spec trap: `Core::send` waits for the core). New Tauri command `post` (`crates/meloet-app/src/main.rs`, in `generate_handler!` and the capability's description) → `CoreHandle::post` → `Core::post`, which puts `Input::Command` on the core's channel with no reply. The bridge has `Transport.post` / `Connection.post` / `post()` (resolves once Rust has it), `state/app.svelte.ts` has `post`, and `KeyDeps.post` (falls back to `send`). Both `send` and `post` are sync Tauri commands, so both run on the main thread in the order the IPC requests arrive, and go into the same channel: a key and a `playStop` keep their order.
- **Core thread** (`crates/meloet-core/src/service/typed.rs`): `Worker::run` takes `Command::TypedKey` before `handle` (answering a `send` with the rev as it is). Reasons: no view is built and diffed per key, an AI-link batch (`state/ai.rs` `hold_of` holds every `Input::Command`) does not hold a key back, and the notice on the status line stays. `typed_key` does nothing while the rules have it off (`Model::typed_keys`). `TypedHands` keeps a `u128` of the notes held: a press of a held note or a release of a note not held changes nothing (so a repeat that came anyway does not sound again), a note above 127 is dropped. NoteOn at `TYPED_KEY_VELOCITY` through the same `fixed()` as the MIDI thread (so the fixed velocity holds). The time: never later than now, more than `MAX_AGE_US` (250 ms) old → now, and never before the last typed event (the ring must stay in order, see the engine; and a late press raised to now must not come after its release). Then the very function of the MIDI thread, `play_key(event, t_us, shared, ring, hub, tx)`, with the engine handle's typed ring: into the engine while a stream is open, the `Held` atomics (the input meter, and R1's `HeldNow`), `Event::Note` to the screen at once, `KeyWhileLoading`.
- **Engine** (`crates/meloet-engine/src/engine.rs`): a second ring of `MidiIn` (`TYPED_RING` = 256). Its producer lives in the `EngineHandle` (`EngineHandle::typed_in() -> &mut MidiFeed`), which only the core thread holds, so the MIDI ring keeps its one producer and `rebuild` makes a new typed ring with the handle (`EngineParts` did not change). `read_midi` reads both rings in the order of `t_us` (peek both heads, the earlier first, the MIDI ring on a tie), each through `key_in` → `stamp_played`: the sound on the play target, the recording (`stamp`), and R1's `Recent`. So `Engine::stop`'s `read_midi(timing, t_us)` splits typed keys by time as it does MIDI keys. No allocation, no lock: `peek` / `pop` of rtrb 0.4.1 are atomics only; `every_transport_path_stays_off_the_allocator` now pushes typed keys too.
- **`LatencyRecord` is the MIDI keyboard's only**: it is written in `read_midi` for the MIDI ring's NoteOns, not in `key_in`. It feeds the measured latency of the sound settings (`Input::LatencySample`) and the dev-hooks key-to-sound log; a typed key's time is the screen's, so it would add the webview's delay to the number the settings show.
- **The switch** (`Command::TypedKeys {on}`; the rules in `crates/meloet-core/src/state/typed.rs`): not a step; taken while recording too. On, the model holds the PC keyboard as a `meloet_midi::Keyboard` (id `TYPED_KEYBOARD_ID`, no name, client and port −1) after the ones plugged in (`all_keyboards()`), so `active_keyboard` (played last, else plugged in last), `KeyboardPlayed`, `chooser_shown` (spec: it counts as 「鍵盤が1台以上」) and the view's list all see it. The view gives it an empty name and address: the screen names it. `audio.midiInput` stays the MIDI keyboard's (none while the PC keyboard is the one shown). Off: it leaves the list, and `played` is forgotten if it was the PC keyboard (back to the MIDI keyboard played or plugged in last; `lost` is not touched).
- **Off lets go** in two places: the screen sends the releases of its held keys before the switch (`switchTypedKeys`, used by Mod K, the button, the menu row and Esc), so they go at once even if the switch waits behind an AI-link batch; and after every input the worker (`follow_typed`, before the view is published) sees the rules turn it off and lets go of every note it still holds (NoteOff at now, through `play_key`). `Effect::AllNotesOff` (keyboard pulled out, MIDI stopped) forgets the held notes.
- **Which keyboard is shown as played**: on a typed press, when the model's active keyboard is not the PC keyboard, the worker handles `Input::KeyboardPlayed { id: TYPED_KEYBOARD_ID }` (only then a view is built). `Shared::typed_played` (set on every typed press and when it is turned off) makes the MIDI thread say its keyboard at its next NoteOn even when it is the one it said last (its `last_played` cannot know the PC keyboard was played in between).
- **The status line** (`StatusMessage::TypedKeysOn`): while on, after the passing lines (notices, audition, 「音が大きすぎます」, the new version, 「見つかりました」 while no output is chosen, the sound pack's question, 「新しい曲」) and before 「やりなおせます」, the parameters' line and the summary. Recording and the count-in say theirs over it.
- **The input meter**: the switch 「キーで弾く」 (`.switch`, the look of 「固定」: accent while on) right of the keyboard's name, then 「オクターブ」 over the note of A (「C3」) while on. `meterFit` takes their widths (`typed: [switch, octave]`, each with its gap) and fits everything else as if they were not there; they are shown, the switch first, only in the room that is left (`MeterFit.typed`: how many). So they never hide a part the spec shows. Not in the split form (a vocal track) nor beside the sound pack's question.
- **Names on the screen**: `ui/src/components/keyboardName.ts` (`keyboardName(k)` for list items, `namedKeyboard(name)` for `keyboardFound`, where Rust's empty name is the PC keyboard) in the input meter (name and the hover list), the status line (「入口」 and 「見つかりました」) and the sound settings' list of keyboards.
- **The seam for E2 (arpeggio)**: typed keys reach the engine exactly as MIDI keys do (`read_midi` → `key_in` → `stamp_played`), so an arpeggio that works on what `key_in` gets for the play target treats both alike. A third source of keys needs only another ring in the handle and one more head in `read_midi`'s merge.
- **Traps**: (1) Tauri 2.12.5 runs a command that is not `async` on the main thread (tauri-macros 2.7.4 `body_blocking`; IPC on Linux is a `fetch` POST to the `ipc:` scheme, `scripts/ipc-protocol.js`), so `post` must stay as cheap as `send`'s hand-over. That WebKitGTK hands the scheme's requests to the main thread in the order they were made is read, not proven (a key's release reordered before its press would leave a note sounding until the key is pressed again or the switch goes off). (2) In jsdom nothing is laid out: the input meter tests set `clientWidth` (on `HTMLElement.prototype`; jsdom has it on `Element.prototype`). (3) `npm` tests: the fake's `post` sends, and `tests/fake-app.svelte.ts` has `post` / `posted`.

## Spec rules

For `docs/spec/3-bands.md`, "Rules added in round 12":

- 「キーで弾く」 (Mod K, the switch in the input meter, 「再生 ▸ キーで弾く」 with a check mark, and Esc while it is on) lets the PC keyboard play the keys track as a keyboard. Off at start; not kept.
- Keys by their place: white keys A S D F G H J K L ; are C D E F G A B C D E, black keys W E are C# D#, T Y U are F# G# A#, O P are C# D# of the next octave. Z and X lower and raise the octave of A, from C0 to C7 (C3 at first, kept while meloet runs). Changing the octave lets go of the keys held.
- Velocity 100, or the fixed velocity.
- While it is on, letters and digits (also the number pad's) without a modifier are not shortcuts, also those that play nothing. Keys with Mod, with Shift (Shift R, Shift M …), Space, arrows, Delete, Home, Enter, Tab, F keys and Esc work as before. While text is typed the letters go into the box.
- A key held does not sound again when it repeats; letting go of it ends its note. When the window loses the keys (another window in front, hidden), and when it is turned off, every key held is let go.
- Keys the input method takes (Japanese input on) do not sound; the status line says so.
- It sounds, shows on the input meter, records, and is kept by 「さっきのを残す」 like a MIDI keyboard. A recorded key takes the position heard when the key event happened in the page.
- 「パソコンのキーボード」 is in the list of keyboards (input meter, sound settings) only while it is on, after the keyboards plugged in. It counts as a keyboard for the output chooser. The input meter shows it while it was played last (or no keyboard was played yet); a key of a MIDI keyboard shows that one again.
- Esc order: after stopping a drag, the file drag, the box being typed in, and the tips and menus; before the dialogs, the shelf and the bands (「ひとつ戻る」).
- The status line while on: 「キーで弾く：オン。1文字のショートカットは止まっています。Z ／ X でオクターブ、Esc でやめる ・ 日本語入力がオンだと鳴りません」, under what is said for the moment (notices, recording, the output not chosen) and over 「やりなおせます」 and the summary.
- In the input meter, the switch 「キーで弾く」 right of the keyboard's name (accent while on), and while on 「オクターブ」 with the note of A. Both take only room that is left after everything the meter showed before: the switch first, then the octave. At 1280 × 800 at 100 % the switch shows and the octave does not; at 150 % neither (Mod K, the menu and the status line still work). Not shown in the split form or with the sound pack's question.
- No step name (not a step).

`docs/spec/4-keys.md`: a row "Play with the PC keyboard on / off (「キーで弾く」)" | <kbd>Mod</kbd> <kbd>K</kbd> | <kbd>Mod</kbd> <kbd>K</kbd> | Works. And a sentence under the table's notes: "While 「キーで弾く」 is on, keys marked one letter and the digit keys do not work (they play notes, or nothing); see spec 3."

## Readings

- **Shift + a letter is not the PC keyboard's.** The spec stops letters "without a modifier"; Shift is a modifier, so Shift R (さっきのを残す), Shift M, Shift S, Shift T work while it is on, and Shift + A plays nothing. Ctrl, Alt and Meta likewise.
- **Digits** are the row's and the number pad's (the tool keys 1 2 3 read both).
- **Z at C0, X at C7**: nothing happens (still not a shortcut); the keys held are let go only when the octave really changes.
- **The octave is kept while meloet runs** (also after off and on); it starts at C3. The spec says only that the switch is off at start.
- **The 「音が出ました」 hint** is not put away by the PC keyboard's keys (they are a keyboard: "any action other than the keyboard" clears it). Other keys clear it as before.
- **IME**: `isComposing` keys are dropped as before; a key whose `key` is `Process` (the input method took it) is neither a note nor a shortcut. Its default is not prevented (the input method has it).
- **`TypedKey` leaves the notice**: it is added to `SetViewport | Audition | AuditionOff` in `state.rs` (and in practice never reaches the rules). A key is played like a keyboard's, and a MIDI key does not put a notice away either. `TypedKeys` (the switch) is a user action and clears it as other commands do.
- **The time limit** of 250 ms (`MAX_AGE_US`): older times are taken as now. The engine's clock keeps 512 blocks (0.34 s at 32 frames); a recorded key whose time it no longer keeps is lost, a late one is only late.
- **No name from Rust**: the PC keyboard's `KeyboardView.name` and `address` are empty, and `StatusMessage::KeyboardFound { keyboard: "" }` is the PC keyboard (when it is the only keyboard and no output is chosen); the screen puts 「パソコンのキーボード」 there.
- **Where the switch is and how it hides**: right of the name, as in the spec's picture; shown only in room left over (the same decision the lead took for R1's button: a new control does not push out what the spec and the mocks show). Question for the owner: at 1280 × 800 at 100 % only the switch shows (not 「オクターブ C3」), and at 150 % neither; is that right?
- **The menu row** 「キーで弾く」 (`menu.typedKeys`, the spec's word) is the last row of 「再生」, with Mod K and a check mark while on. The spec does not say which menu; the key list puts it in 「再生と録音」.
- **Wording** (`ui/src/text/ja.ts`): `input.typedKeys` 「キーで弾く」, `input.typedKeyboard` 「パソコンのキーボード」, `input.octave` 「オクターブ」, `menu.typedKeys` 「キーで弾く」, `msg.typedKeysOn` (the spec's whole status text), all `user:2026-11-23`. Made up: `msg.typedKeysIme` 「日本語入力がオンだと鳴りません」 (`builder:2026-11-24`; the spec asks the hint to say it, in these words in its prose), joined to the spec's text with 「 ・ 」 so the spec's text stays as written. The key list reuses `keyList.playByKeys` / `key.playByKeys` of G1.
- **Not built from the spec's picture**: 「Z ／ X で上下 ・ Esc でやめる」 next to the octave and 「オンの間、1文字のショートカット（A、E、M など）は止まります」 under the keys (the status line says both), and the picture of the 13 keys. The text of the spec asks only for the switch and 「オクターブ C3」.
- **Turned on while no output is chosen**: the output chooser comes up (the spec's 「鍵盤が1台以上」); keys do not sound until an output is open (no stream: nothing goes into the engine, as for a MIDI key).
- **`WAVE2_ROWS`** is gone (it held only this row); the type check that every `KeyAction` has a row stays (`ACTION_ROWS` is a `Record` of every kind). Its uses in the R1 and A1 tests were taken out.
- **Fake** (`ui/src/bridge/fakeTyped.ts`): the switch (the list, `typedKeysOn` on the status line, back to the scene's line when off) and the keys told back as note events at 100 or the fixed velocity; `TYPED_KEY_VELOCITY` is copied there (it is not in `ui/src/bridge/generated/`). Scenes `typedKeys` (played, with a MIDI keyboard too: 「パソコンのキーボード +1」, keys held C3 E3 G3) and `typedKeysSettings` (the sound settings' list).

## Measurements

None (the PC was not quiet; the brief says the lead measures after the merge).

**What the lead must measure on a quiet PC** (spec 1-4: the input and the audio thread were touched):

- `tools/measure/latency.sh --state stopped|playing|recording` and `tools/measure/record-timing.sh private` (and `keep`): `read_midi` now peeks a second ring for every event, and `LatencyRecord` moved into it. Expect the same numbers as before.
- **Key → sound for a typed key** (no tool yet; the spec's aim: the MIDI keyboard's latency plus one frame or less). Two ways:
  1. Whole way, with `tools/measure/remote.py`: start the app (`App(out)`), turn 「キーで弾く」 on (`app.send({"type": "typedKeys", "on": true})`), give the window the keys (`X.focus`), and press a letter with a made-up X key event at a known CLOCK_MONOTONIC time while recording the output (the `Recorder` class there, or the private PipeWire of `record-timing.sh`). `X` now sends only pointer events; a key event needs an `XTestFakeKeyEvent` (libXtst, as `xdotool key`) through XWayland, or `XSendEvent` of a `KeyPress` to the window (GTK may drop sent key events; check). Time from the X event to the onset in the recording, against the same for `meloet-vkeys` (MIDI).
  2. Page → sound only, with `MELOET_UI_SCRIPT` (`ui/src/dev/`): dispatch `KeyboardEvent`s with `code: "KeyA"` on `document` and log `performance.now()`; misses the time from the X server to the page.
  Also worth reading: `typedKey.tUs` (the event time on Rust's clock) against the time the core takes it (the webview → core delay), e.g. with a dev-hooks log; that delay decides whether 250 ms is ever reached.
- `tools/measure/webkit-damage.sh` is not needed: nothing new changes at 60 Hz (the switch and the octave change only when pressed).

## Left for later

- **Not checked in the real app** (no run of the app, by hand or by ear): the keys sounding, the IME behaviour of WebKitGTK (`isComposing` / `Process`), that `KeyboardEvent.timeStamp` in WebKitGTK 2.52 is on `performance.now()`'s clock (guarded: more than 1 s away → now), which moment it stands for (when GTK got the key, or when the page did), and that blur / `visibilitychange` come when another window takes the keys. `scripts/check-all.sh` was not run.
- **AI-link batch**: `TypedKeys` (the switch) waits behind an open batch like every command (`hold_of`); the keys themselves do not. Off still lets go at once from the screen.
- **A ring full** (`play_key` drops a push that does not fit): a dropped NoteOff leaves a note sounding. Same as the MIDI ring; 256 slots and human typing make it unlikely.
- **Two keyboards on one note**: a release from either lets go of the note in `Held` (the meter), as with two MIDI keyboards before.
- `meterFit`'s new field changed the `ALL` constant of `ui/tests/meter-fit.test.ts` (`typed: 0`).
